D3 · II: RAG, retrieval, latency & observability

Match retrieval to the shape of the data, pay for latency only where users feel it, and make every agent step visible without leaking what users said.

≈ 18 minutes 3 review + 1 recall + 13 questions + 1 scenario D3

What the blueprint asks. Four D3 task statements: RAG pipeline chunking and indexing; retrieval strategies matched to data shape and query pattern; accuracy–latency trade-offs; observability and monitoring at scale. Exam guide §6, D3. An official sample item has a RAG system degrade after a document refresh: the heuristic is diagnose what changed (retrieval/indexing) before blaming the model. Blueprint: answer heuristics.

0 · Spaced review

An internal bot answers employee questions from a fixed set of 40 policy documents: retrieve relevant passages, then answer. A stakeholder asks for "a multi-agent system so it feels smarter". What do you recommend?

  1. A single augmented-LLM call with retrieval, measured against your evals
  2. An orchestrator with one research subagent assigned to each document
  3. An autonomous agent loop with a generous maximum iteration cap
  4. A voting ensemble that answers every question three separate times
Start with the simplest solution; a single augmented-LLM call with retrieval is often enough. Multi-agent used ~15× chat tokens in Anthropic's research system (June 2025, Opus 4 lead + Sonnet 4 subagents) and suits breadth-first, parallelisable work, not a fixed retrieve-then-answer flow. Building effective agents; Multi-agent research system.

A RAG assistant sends tool definitions, a 6k-token static system prompt, then retrieved chunks and the question. Prompt caching is on, yet cache_read_input_tokens is always 0. The system prompt begins with the current timestamp. Best fix?

  1. Move the timestamp after the static content, then cache it
  2. Switch the 5-minute cache lifetime to the 1-hour cache lifetime
  3. Shorten the system prompt below the minimum cacheable token length
  4. Add more cache breakpoints so every block gets cached separately
The cache is a prefix in the order tools → system → messages; a change at one level invalidates that level and everything after it. A timestamp at the top changes every request, so nothing ever matches. Static first, dynamic last. A longer TTL or more breakpoints can't help a prefix that never repeats. Prompt caching.

An HR-policy Q&A agent has four tools: search_policies, read_policy, update_employee_record, send_email. It only ever needs to answer questions. A security review flags the design. Best response?

  1. Remove the record-update and email tools from this agent entirely
  2. Keep all four tools but log every call for auditing
  3. Keep all four tools but require user confirmation before writes
  4. Keep all four tools; add a prompt warning against writes
Remove, don't monitor. Least privilege means dropping tools the job doesn't need. Logging or confirmations still leave the capability exposed to prompt injection or error. Fewer, purpose-built tools also help the agent pick correctly. Blueprint heuristics; Writing tools for agents.

1 · Recall first

Without looking: (a) What does Contextual Retrieval do to each chunk, and roughly how much did it cut top-20 retrieval failures (embeddings only / + BM25 / + reranking)? (b) Below what corpus size does Anthropic say you can skip RAG entirely? (c) Name four levers that cut latency. (d) By default, should an OpenTelemetry GenAI instrumentation record prompts and completions?

(a) An LLM writes 50–100 tokens of chunk-specific context (from the whole document) and prepends it to the chunk before embedding and BM25 indexing. Failure rate 5.7% → 3.7% (−35%) with contextual embeddings; → 2.9% (−49%) adding contextual BM25; → 1.9% (−67%) adding reranking.
(b) Under ~200k tokens (~500 pages): put the whole knowledge base in the prompt, with prompt caching.
(c) Smaller/faster model (Haiku 5.5) or lower effort; fewer input and output tokens (concise prompt, max_tokens); streaming (better perceived TTFT); prompt caching of the static prefix; parallel tool calls; fewer reranked candidates; fast mode for output speed on Opus (research preview).
(d) No. Content capture SHOULD be off by default and opt-in; in production, store content externally with separate access controls and record references on spans.

  • ~200k tokens → whole corpus in prompt + caching
  • At least four valid latency levers including streaming and caching

2 · The ideas that matter

Chunking & indexing

Chunks lose context. "The company's revenue grew by 3% over the previous quarter" says neither which company nor when. Chunks are usually no more than a few hundred tokens; chunk size, boundary and overlap all affect retrieval, so treat them as tunables and run evals. Contextual Retrieval. Split on document structure (headings, sections, whole table rows) rather than blind character counts, and keep metadata (source, section, date, product) next to each chunk for filtering and citations. Architect practice; the article only says "consider how you split your documents into chunks".

Contextual Retrieval. Claude reads the whole document plus one chunk and writes 50–100 tokens of situating context, which is prepended to the chunk before both embedding (contextual embeddings) and BM25 indexing (contextual BM25). With prompt caching the one-off cost was ~$1.02 per million document tokens. Top-20 retrieval failure fell 5.7% → 3.7% (−35%) with contextual embeddings, → 2.9% (−49%) adding contextual BM25, → 1.9% (−67%) adding a reranker. Best tested setup: retrieve top 150, rerank, pass top 20 (20 beat 5 and 10). These are the post's Sept 2024 figures; it is still Anthropic's main retrieval write-up. Contextual Retrieval. Alternative: contextualized chunk embedding models (voyage-context-4) embed each chunk with full document context "without manual metadata augmentation", with no LLM step per chunk. Voyage reports its earlier voyage-context-3 beat Contextual Retrieval by 6.76% (vendor benchmark). Embeddings guide; voyage-context-4 blog.

Embeddings: Anthropic doesn't make them. The docs point to Voyage AI (by MongoDB) but say to assess several vendors. Current Voyage picks: voyage-4-large / voyage-4 / voyage-4-lite (quality → cost), voyage-code-4, voyage-law-2, voyage-finance-2, voyage-multimodal-3.5 (text, images, video), voyage-context-4; rerankers rerank-3 and rerank-3-lite (latency/cost). Always set input_type to query or document. Embeddings guide. Rerank 3 (Sept 2026) upgrades in place: no re-indexing, and scores are calibrated so Rerank 2.5 thresholds still work. Rerank 3 blog. Consistency: queries must be embedded in the same vector space as the index. The four general Voyage 4 models (large, base, lite, nano) share one space, so you can change the query model "without re-vectorizing documents"; any other model change (including to voyage-code-4 or voyage-context-4, which that claim doesn't cover) means re-embedding the corpus. Voyage 4 blog. After any content refresh, check that new documents went through the same chunker, contextualizer and embedding model as the rest.

Putting retrieved text in the prompt. For 20k+ token inputs, place long documents at the top, above the query and instructions (queries at the end improved quality by up to 30% in Anthropic's tests); wrap each in <document> tags with <source> metadata; for long-document tasks ask Claude to quote relevant parts first. Prompting best practices: long context.

Citations. All active models support it. Pass chunks as document blocks (plain text/PDF auto-chunked into sentences; custom content used as-is; inline or by Files API file_id) or as search_result blocks (from a tool result or top-level) with citations enabled. Pointers are guaranteed valid, citation quality beat prompt-based quoting in Anthropic's evals, and cited_text doesn't count toward output tokens. Works with prompt caching and batch; incompatible with structured outputs (400 error). Citations; Search results.

Observability at scale

Why it's hard. "Agents make dynamic decisions and are non-deterministic between runs, even with identical prompts", and they are stateful, so errors compound. Anthropic added full production tracing to diagnose failures, built resume-from-failure, and used rainbow deployments so updates don't break agents mid-run. They monitored "agent decision patterns and interaction structures" without monitoring individual conversation contents. Multi-agent research system (June 2025).

OpenTelemetry GenAI conventions (status: Development; maintained in the semantic-conventions-genai repo) define spans for inference, embeddings, retrieval, memory operations, invoke_agent and execute_tool. Metrics include gen_ai.client.inference.duration, gen_ai.client.inference.time_to_first_chunk (client-side TTFT), gen_ai.server.time_to_first_token, gen_ai.execute_tool.duration and token counters gen_ai.client.inference.usage.* (input, output, cache_read, cache_write, reasoning). gen_ai.client.operation.duration remains for non-inference operations. Prompts and outputs are sensitive and large: instrumentations SHOULD NOT capture them by default (opt-in); production pattern = store content externally with separate access controls and put references on spans. GenAI spans; Client inference; GenAI metrics; Token metrics; Agent spans.

Fleet-level usage and cost. The Usage & Cost Admin API (Admin key; not workspace keys) reports tokens (uncached, cached, cache creation, output) and server-tool use via /v1/organizations/usage_report/messages, grouped by model, workspace, API key, service tier and more, in 1-minute to 1-day buckets; /v1/organizations/cost_report gives daily USD by workspace or description. Data typically lands within 5 minutes. Datadog, Grafana Cloud, Honeycomb and others offer ready-made integrations; Claude Code per-user costs come from the Claude Code Analytics API. Usage and Cost API.

What to watch. Latency p50/p95 and TTFT; input/output/cache tokens and cost per request; error rate and tool-failure rate (tool results with is_error); retrieval quality (hit rate on a labelled set) and drift in query mix or answer quality over time, sampled with LLM-as-judge plus human review. is_error; LLM-as-judge; drift and p95 are standard SRE practice, not from an Anthropic source.

3 · Practice

A financial-filings RAG system retrieves chunks like "Revenue grew 3% over the previous quarter" for questions about the wrong company. Chunking is otherwise sensible. Which change targets the root cause most directly?

  1. Prepend LLM-generated document context to each chunk before indexing it
  2. Switch the answering model to the most capable available tier
  3. Increase retrieved chunks per query from twenty to one hundred
  4. Instruct the model in the prompt to ignore irrelevant chunks
The chunk lacks which company and when. Contextual Retrieval prepends 50–100 tokens of situating context before embedding and BM25 indexing, cutting retrieval failures 35–49% (67% with reranking). A bigger model or prompt can't fix chunks that were never retrieved correctly; more chunks adds noise and cost. Contextual Retrieval.

Support engineers search a knowledge base with queries like "E-4471 after firmware 2.3". Pure embedding search returns articles about error codes in general but often misses the exact code. Best fix?

  1. Combine BM25 lexical retrieval with embedding search using rank fusion
  2. Replace the embedding model with a larger general-purpose embedding model
  3. Lower the similarity threshold so more embedding results are returned
  4. Fine-tune the answering model on all historical support ticket transcripts
Exact identifiers are a lexical problem. Anthropic's example: "Error code TS-999" where embeddings miss the exact match. Hybrid = BM25 + embeddings, combined and deduplicated with rank fusion. A larger embedding model is still semantic; a lower threshold adds noise. Contextual Retrieval.

A startup wants a vector database for its 120-page employee handbook (≈ 60k tokens), queried a few hundred times a day. What do you recommend?

  1. Put the whole handbook in the prompt with prompt caching
  2. Build hybrid retrieval with contextual embeddings and a reranker stage
  3. Fine-tune a small model on the handbook, skipping retrieval entirely
  4. Use an agent that greps the handbook for every question
Anthropic: under ~200k tokens (~500 pages), include the whole knowledge base in the prompt; caching makes repeat calls faster and cheaper. RAG infrastructure here is complexity without benefit. Contextual Retrieval; Prompt caching.

Managers ask a sales assistant questions like "What were total refunds for the EMEA region last quarter versus the prior one?" Order data lives in a Postgres warehouse. The team embedded every order row into a vector store and answers are wrong. Best redesign?

  1. Give Claude a read-only query tool over the warehouse tables
  2. Re-chunk the order rows into larger batches before embedding them
  3. Add a reranker so the most relevant rows rank first
  4. Switch to a domain-specific finance embedding model for the rows
Aggregation over structured data is a data-shape mismatch: similarity search returns similar rows, it can't sum, filter by period or compare. A scoped, read-only SQL/API tool computes the exact answer (keep it least-privilege). Every other option tunes the wrong mechanism. Exam guide D3: retrieval matched to data shape.

A coding agent answers questions about a monorepo that receives hundreds of commits a day. A nightly embedding index is often stale by noon. Which retrieval approach fits best?

  1. Use just-in-time agentic search with glob, grep and file-read tools
  2. Re-embed the full repository every hour on a fixed schedule
  3. Load the entire monorepo into context for every single question
  4. Keep the nightly index and warn users answers may lag
Claude Code keeps lightweight identifiers and retrieves files just in time with glob and grep, "effectively bypassing the issues of stale indexing". Trade-off: runtime exploration is slower than pre-computed retrieval. A large repo won't fit in context, and hourly re-embedding is costly and still stale. Context engineering.

After last week's documentation refresh, a product-support RAG assistant gives vague or wrong answers about the updated products only. Model, prompts and code are unchanged. Which two causes should you investigate first?

  1. The refreshed documents were embedded with a different embedding model
  2. New documents' tables and headings were split badly during chunking
  3. The answering model's temperature setting has drifted higher since deployment
  4. The system prompt now exceeds the model's comfortable context length
Diagnose what changed: only the documents did, so check the indexing path. Vectors from an embedding model outside the query model's shared space (only the four general Voyage 4 models share one) aren't comparable; a new doc format can break structure-aware chunking. Temperature and prompt length didn't change, and wouldn't hit only the updated products. Blueprint heuristics; Voyage 4 (shared vs separate spaces).

A compliance team needs every answer from a policy assistant to link to the exact supporting passages, with a guarantee that pointers are valid. The current design asks Claude to return quotes inside a structured-output JSON schema. What do you recommend?

  1. Use the Citations feature with documents and drop structured outputs
  2. Keep structured outputs but add a stricter schema quote field
  3. Ask Claude to repeat each quote for later string matching
  4. Raise the temperature so the model explores more source passages
The Citations API parses citations so pointers are guaranteed valid, picks more relevant quotes than prompt-based approaches, and cited_text doesn't count toward output tokens. Citations and structured outputs are incompatible (400 error), so the schema has to go for this path. Citations.

A customer-facing chat assistant has a 5k-token static system prompt and tool set. Users complain it "feels frozen" before answers appear. Which two changes most improve perceived latency without lowering answer quality?

  1. Stream the response so text appears as it is generated
  2. Cache the static system prompt and tools with prompt caching
  3. Raise retrieved chunks to fifty so fewer follow-up questions occur
  4. Ask for an exact word count limit on every response
Streaming improves TTFT, the delay users feel. Caching a long stable prefix improves time-to-first-token and cuts input cost. Fifty chunks adds input tokens (slower). Word-count limits are less effective than sentence or paragraph limits because models count tokens. Reducing latency; Prompt caching.

Your pipeline retrieves 150 candidates, reranks, and passes the top 20 to Claude. An engineer proposes reranking 1,000 candidates "for maximum accuracy" in an interactive app with a 2-second budget. What is the architect's response?

  1. Measure accuracy and latency on evals before changing the setting
  2. Approve it, because reranking more candidates is always worth it
  3. Remove the reranker, because any reranking breaks the latency budget
  4. Approve it, but double the model's maximum output token limit
Reranking more chunks can improve accuracy but adds latency and cost; Anthropic advises experimenting with settings for your use case. Justify configuration with measured accuracy vs p95 latency, not intuition (a latency-optimised reranker such as rerank-3-lite is one more variant to test). "Always worth it" ignores the budget; removing the reranker throws away measured accuracy; output tokens have nothing to do with reranking. Contextual Retrieval; Embeddings guide (rerankers).

Every night a retailer summarises 40,000 product reviews for a dashboard read the next morning. All requests share a long instruction prefix. Which configuration is most cost-effective?

  1. Message Batches API with prompt caching on the shared prefix
  2. Real-time streaming calls on the most capable model currently available
  3. Parallel real-time calls using as many concurrent workers as possible
  4. Real-time calls with a five-minute prompt cache on each request
Nobody is waiting, so batch: 50% cheaper, most batches done within an hour (max 24 h). Batch and caching discounts stack; use the 1-hour TTL because batches can take longer than 5 minutes. Streaming and parallel workers buy latency you don't need. Batch processing.

A health-insurer runs a multi-agent claims assistant in production. Failures are intermittent and hard to reproduce. Member data is regulated. Which two monitoring choices are most appropriate?

  1. Trace agent invocations and tool calls as linked OpenTelemetry spans
  2. Store prompt content separately under access control, referenced from spans
  3. Write full prompts and outputs into the shared application logs
  4. Reproduce failures by rerunning the same prompt at temperature zero
Tracing agent and tool steps (OTel invoke_agent / execute_tool spans) is how Anthropic diagnosed agent failures. OTel says content capture SHOULD be off by default and, in production, stored externally with separate access controls. Shared logs leak PHI. Agents are non-deterministic even with identical prompts, so reruns won't reliably reproduce. Multi-agent research system; OTel GenAI spans.

A research agent's tasks run for 20–40 minutes across many tool calls. Each deploy of a new prompt version breaks in-flight runs. Which deployment approach did Anthropic use for exactly this?

  1. Rainbow deployments that shift traffic while old versions keep running
  2. Blue-green deployments that switch all traffic over at one instant
  3. Nightly maintenance windows that pause all running agents before deploying
  4. Feature flags that hot-swap new prompts inside every running agent
Agents are long-running and stateful, so Anthropic used rainbow deployments: gradually shift traffic from old to new versions while both run. An instant switch or hot-swap breaks agents mid-task. Multi-agent research system.

Finance wants a weekly Claude API cost and token breakdown per product team; each team has its own workspace. Engineers propose summing usage fields from every application log. What is the better source?

  1. The Usage and Cost Admin API, grouped by workspace
  2. Sampled OTel spans with the full prompt content captured
  3. A nightly batch job asking Claude to estimate spend
  4. Workspace API keys calling the usage endpoint per team
The Usage & Cost Admin API returns organisation-wide token usage (including cache reads and writes) and USD cost, groupable by workspace, model and API key, for reconciling with Anthropic billing; the docs pitch it as precise counts "instead of relying solely on response token counting" (what log summing is). Sampled spans undercount and capturing content adds privacy risk without improving cost data. Claude can't estimate your bill. Workspace API keys don't work on these endpoints: they need an Admin API credential. Usage and Cost API.

4 · Architect scenario

Tessaro Medical services infusion pumps in 900 hospitals. Field technicians want a mobile assistant that answers repair questions. Sources: 30k pages of PDF service manuals (heavy on tables, part numbers and fault codes, updated monthly), a Postgres parts-inventory and warranty database, and past service tickets that contain patient-adjacent data. Targets: first words on screen within 1.5 s, every repair step cited to a manual page, and the VP of Service wants a weekly report on quality and cost. A pilot that embedded everything into one vector index got fault-code questions wrong and quoted stale part numbers after the last manual update.

(8 min) (a) How do you chunk and index the manuals, and what does the monthly update process need? (b) Which retrieval strategy for each source? (c) How do you hit the 1.5 s target and justify the configuration? (d) What do you monitor, and how do you handle ticket content in telemetry?

(a) Structure-aware chunks per section/procedure; keep tables and fault-code rows intact; metadata: manual, model, revision, page. Apply contextual retrieval (prepend model + section context before embedding and BM25). Monthly: re-index changed manuals through the same chunker, contextualizer and embedding model; retire superseded revisions; run a retrieval eval before switching the index live.
(b) Manuals: hybrid BM25 + embeddings (fault codes and part numbers are exact tokens), rerank to a small top-k. Inventory/warranty: a read-only SQL/API tool, never embeddings, so stock and part numbers are live. Tickets: optional, only after redaction, and kept out of the answer path unless evals show value.
(c) Streaming for TTFT; cache the static system prompt and tools; a fast tier (or routing) for simple lookups; issue the retrieval and inventory calls in parallel; tune reranker candidates and top-k (or a lite reranker) on an eval set against p95 TTFT. Fast mode won't help here: it speeds output, not TTFT. Return chunks as search_result/documents with citations enabled (no structured outputs on that call).
(d) Trace each request: retrieval, rerank, tool and model spans (OTel GenAI). Metrics: p95 TTFT and total latency, tokens incl. cache reads, cost per answer, tool error rate, citation coverage, retrieval hit rate on a labelled set, technician thumbs-down rate, drift after each manual update. VP's weekly cost view: the Usage & Cost Admin API (by model/workspace) joined with the quality metrics. Content capture off by default; when needed, redact and store externally with restricted access, referenced from spans.

  • Structure-aware chunking + metadata (revision/page); contextual retrieval
  • Update process re-indexes with the same pipeline and runs evals before cut-over
  • Hybrid lexical + semantic for codes; rerank
  • Structured inventory via a query tool, not embeddings
  • Streaming + caching + parallel calls; config justified by evals vs p95
  • Citations enabled; aware of structured-output incompatibility
  • Tracing + latency/cost/error/quality metrics (cost via Usage & Cost API); content off by default, external and access-controlled
