D7: Developer productivity with Claude Code

You already use Claude Code daily. The exam asks the team version: which file wins, what actually enforces a rule, and how to run it safely in CI and on a cloud provider.

0 · Spaced review

A logistics firm asks for an "AI agent" that every night pulls the same three reports, reconciles totals, and emails a summary. The steps never change. What do you propose?

  1. A fixed prompt chain with programmatic checks between steps
  2. An autonomous agent that plans its own steps nightly
  3. A multi-agent system with one subagent for each report
  4. An orchestrator that delegates the reports to parallel workers
Known, fixed steps = workflow (prompt chaining), not an agent; agents are for open-ended problems where steps can't be predicted. The autonomous and orchestrator options add cost and error compounding for no gain; multi-agent is for broad parallel exploration. Anthropic, Building effective agents.

An assistant's system prompt starts with the current timestamp, followed by 6k tokens of fixed instructions and tool definitions. Cache reads are almost zero. Best fix?

  1. Move the timestamp after the static instructions and tools
  2. Switch every single request to the one-hour cache TTL
  3. Add a fifth cache breakpoint just around the timestamp
  4. Upgrade to a larger model with a longer context
Caching matches an exact prefix (tools → system → messages); any change early in the prefix is a miss for everything after it. Put static content first, dynamic last. A longer TTL doesn't help when the prefix changes every call; the limit is 4 breakpoints; model size is irrelevant. Prompt caching docs.

A read-only reporting agent was given a delete_record tool "just in case". Security flags it. What is the least-privilege answer?

  1. Remove the tool from the agent's tool list entirely
  2. Keep the tool but log every call for audit
  3. Keep the tool but require human confirmation each time
  4. Keep the tool and warn against it in prompts
Official sample heuristic: remove, don't monitor. A tool the task never needs should not exist in the agent's context; logging, confirmation and prompt warnings all leave the capability in place. Claude Code mirrors this: a bare tool deny removes the tool from context. Blueprint heuristics; Claude Code permissions.

1 · Recall first

Without looking: (1) list the Claude Code settings levels from highest to lowest precedence; (2) say which mechanism you'd use for each: a rule that must never be broken, a reusable team workflow invoked by name, a noisy codebase investigation, and a shared MCP server.

(1) Managed (server-managed / MDM / managed-settings.json) > command-line flags > local project .claude/settings.local.json > shared project .claude/settings.json > user ~/.claude/settings.json. Array keys like permissions.allow merge; a deny anywhere beats an allow anywhere. (2) Must-never → PreToolUse hook (exit 2) and/or managed deny rule, not CLAUDE.md. Reusable workflow → skill (.claude/skills/x/SKILL.md, invoked as /x). Noisy investigation → subagent (own context window, returns a summary). Shared MCP → project scope .mcp.json at the repo root. Settings; Best practices.

  • Managed on top, user at the bottom, local above shared project
  • Knows arrays merge and deny wins across scopes
  • Hook (deterministic) for must-never, not CLAUDE.md (advisory)
  • Skill for workflows, subagent for context isolation
  • .mcp.json at repo root for team MCP

2.2 Permissions and modes

Rules are evaluated deny → ask → allow; first match wins and specificity doesn't matter, so an allow can never punch a hole in a deny, and a deny in any scope beats an allow in any scope. Syntax: Bash(npm run *), Read(./secrets/**), WebFetch(domain:github.com), mcp__github__*, Agent(Explore). Bash patterns are string matches: they miss git -C . push, binaries called by path, and sh -c, so pair them with the sandbox or a PreToolUse hook (a hook's exit 2 stops the call before rules are evaluated, so it holds even against an allow rule). .claudeignore does nothing; use Read deny rules. Project allow rules apply only after the workspace-trust dialog, and -p never shows one. Permissions.

2.5 MCP for teams

Shared servers go in .mcp.json at the repo root under mcpServers (claude mcp add --transport http --scope project …); use ${VAR} for secrets. Same name: local > project > user > plugin > claude.ai connectors, whole entry wins. Project servers need per-user approval interactively (reset: claude mcp reset-project-choices) but load without asking in -p. HTTP is the recommended transport; SSE is deprecated. MCP.

2.6 Sandbox: the OS-level backstop

Off by default (/sandbox or sandbox.enabled). Applies to shell commands (Bash, PowerShell, Monitor): macOS Seatbelt, Linux/WSL2 bubblewrap; native Windows runs unsandboxed. Writes limited to cwd and temp; network via a proxy with an empty allowedDomains list. Not sandboxed: Read/Edit/Write/WebFetch tools, hooks, local MCP servers. Enforce with managed {"sandbox":{"enabled":true,"failIfUnavailable":true,"allowUnsandboxedCommands":false}}. The proxy doesn't inspect TLS by default, so broad domains like github.com are an exfiltration path. Permissions + sandbox = defense in depth. Sandboxing.

3 · Practice

Security deploys "deny": ["Read(./.env)"] in managed settings. A developer adds "allow": ["Read(./.env)"] to their .claude/settings.local.json. What happens when Claude tries to read .env?

  1. Blocked, because deny rules win across every scope
  2. Allowed, because local settings override shared project settings
  3. Prompted, because conflicting rules fall back to ask
  4. Allowed, because the more specific rule takes priority
Evaluation is deny → ask → allow, first match wins, and a deny at any level beats an allow at any level. Local-over-project precedence applies to scalar values, not to undoing denies; conflicts don't degrade to ask; specificity is explicitly irrelevant. Permissions.

A platform team wants every engineer who clones a repo to get the same GitHub and Sentry MCP servers, versioned with the code. What should they do?

  1. Commit a .mcp.json at the repository root
  2. Add mcpServers to the shared settings.json file
  3. Put the .mcp.json inside the .claude folder
  4. Each engineer adds servers at user scope
Project scope = .mcp.json at the repo root (claude mcp add --scope project). mcpServers inside settings.json isn't read, a .mcp.json under .claude/ isn't found (both listed as common config bugs), and user scope is neither shared nor versioned. MCP; Debug your config.

CLAUDE.md says "never force-push to main", yet Claude occasionally tries. The team needs a guarantee. What do you add?

  1. A PreToolUse hook that exits with code 2
  2. A stronger CLAUDE.md rule written in all capitals
  3. A PostToolUse hook that reverts the forced push
  4. A PreToolUse hook that exits with code 1
CLAUDE.md is advisory context; hooks are deterministic. A PreToolUse hook that exits 2 blocks the call before permission rules are checked, even if an allow rule matches, and feeds stderr back to Claude. Exit 1 is a non-blocking error by default, so the push proceeds. PostToolUse runs after the push already happened; reverting a force-push is not a guarantee. Hooks; Best practices.

A CI job runs claude -p on pull requests, including PRs that may modify files under .claude/. Which two choices make the run safe and reproducible?

  1. Run with --bare so repo config never loads
  2. Scope --allowedTools narrowly and set the dontAsk mode
  3. Use bypassPermissions so the job never stalls waiting
  4. Rely on the workspace trust dialog for protection
Without --bare, -p runs project hooks and .mcp.json servers even in untrusted folders, so a malicious PR could inject a hook; --bare skips them and is recommended for CI. A narrow --allowedTools with dontAsk auto-denies everything else. bypassPermissions removes all guardrails; -p never shows a trust dialog. Headless; Permissions.

A deny rule Bash(git push *) is in place, but Claude successfully runs git -C . push origin main. Best explanation and fix?

  1. Prefix patterns miss argument variants; add a hook
  2. Deny rules need a session restart to apply
  3. User deny rules lose to project allow rules
  4. The rule needs a trailing double star wildcard
Bash rules are pattern matches on the command string; the docs list git -C . push, binaries called by path and sh -c as cases they miss. Back them with a PreToolUse hook that parses the command, or the sandbox. Deny beats allow in every scope; ** is path syntax, not a fix for argument order. Permissions.

A monorepo's root CLAUDE.md has grown to 450 lines covering every service, and Claude increasingly ignores parts of it. Which two changes help most?

  1. Move area-specific guidance into path-scoped rule files
  2. Turn must-always rules into deterministic hook scripts
  3. Split it into @imports to save context
  4. Copy critical rules into every subdirectory CLAUDE.md
Bloated files get ignored; target under 200 lines. .claude/rules/ with paths: frontmatter loads guidance only when matching files are touched, and anything that must always happen belongs in a hook. Imports still load into context, so they don't save tokens; duplicating rules adds bloat. Memory; Best practices.

Security requires that (a) only org-approved hooks ever run and (b) engineers can install plugins only from the internal marketplace. Which two controls achieve this?

  1. Set allowManagedHooksOnly to true in managed settings
  2. Set strictKnownMarketplaces to only the internal marketplace
  3. Set disableAllHooks to true in project settings
  4. Add the marketplace to extraKnownMarketplaces in repos
allowManagedHooksOnly blocks user, project, local and plugin hooks; strictKnownMarketplaces is a managed-only allowlist of marketplace sources. disableAllHooks in a project file would also kill the approved hooks and is user-editable; extraKnownMarketplaces adds a marketplace but restricts nothing. Managed settings; Plugins for orgs.

Inference must stay in the company's AWS account, so Claude Code runs on Bedrock. After a Claude Code upgrade, engineers' sessions silently moved to a newer, pricier model nobody approved. Best fix?

  1. Pin the default model variables in managed env
  2. Give every engineer a personal Anthropic API key
  3. Deny the new model with a permission rule
  4. Have engineers run /logout and then sign in
Unpinned aliases follow built-in defaults that change between releases (and can lag what your account enables); pinning ANTHROPIC_DEFAULT_{OPUS,SONNET,HAIKU}_MODEL centrally controls when users move to a new model. API keys break the AWS-only requirement; permission rules govern tools, not model choice; /logout isn't available on Bedrock. Bedrock.

Finance wants a dashboard of Claude Code cost per team, for all 200 engineers, without collecting prompt text. What do you set up?

  1. Managed env enabling telemetry plus OTEL_RESOURCE_ATTRIBUTES team tags
  2. A repo settings.json enabling telemetry in every repository
  3. Enable OTEL_LOG_USER_PROMPTS so the prompts reveal team ownership
  4. Have engineers report their weekly spend in surveys
Admins enforce telemetry through the managed settings env block; claude_code.cost.usage can be sliced by resource attributes like team.id. A repo settings file can't enable telemetry; prompt logging is off by default and would violate the no-prompt-text constraint; surveys aren't data. Monitoring; Settings.

An engineer must refactor an unfamiliar auth module touching about 20 files. What is the recommended way to start?

  1. Plan mode first: explore, write a plan, then implement
  2. Ask for the full refactor in one detailed prompt
  3. Enable bypassPermissions so all the edits finish without interruptions
  4. Write a longer CLAUDE.md describing the whole auth module
Explore → Plan → Implement → Commit, using plan mode, is the documented approach when the change is non-trivial or the code unfamiliar. One giant prompt skips exploration; bypassPermissions is for isolated containers and removes checks; bloating CLAUDE.md costs context in every session. Best practices.

A long session has drifted: Claude repeats the same mistake after two corrections and the context is full of failed attempts. Best next move?

  1. Run /clear and restart with a sharper prompt
  2. Keep correcting until the model finally gets it
  3. Switch to a larger model in this session
  4. Add each failed correction to the root CLAUDE.md
The best-practices guide names "correcting over and over" as a failure pattern: after two failed corrections, /clear and write a better initial prompt with what you learned. More corrections pile on polluted context; a bigger model doesn't clear the context; stuffing CLAUDE.md with one-off corrections bloats it. Best practices.

A repo's .mcp.json defines a stdio server with "command": "./tools/mcp-server". It works for its author but not for a teammate. Which two causes are most likely?

  1. The command uses a relative path to the binary
  2. The teammate earlier dismissed the project server approval prompt
  3. Project scoped servers must use the deprecated sse transport
  4. The sandbox blocks every stdio MCP server by default
Relative paths in command/args and a dismissed approval prompt are both listed MCP failure causes; fix with an absolute or ${VAR} path and claude mcp reset-project-choices, and diagnose with /mcp and claude --debug=mcp. SSE is deprecated, not required; MCP servers run outside the sandbox. Debug your config; MCP; Sandboxing.

4 · Architect scenario

Halyard Payments (made-up) is rolling Claude Code out to 200 engineers on macOS and Linux laptops. Constraints: PCI scope, so inference must stay in its AWS account; repos contain .env files and a secrets/ folder; security wants no unapproved MCP servers or plugins and an audit trail; finance wants cost per team; CI on GitHub Actions should review every PR. Engineers already have personal habits and some use --dangerously-skip-permissions.

Design the rollout: where each control lives (managed vs repo vs user), how secrets and dangerous commands are stopped, how MCP and plugins are governed, provider and telemetry setup, and the CI design. Name the specific settings.

Managed settings via MDM (top precedence, users can't override): CLAUDE_CODE_USE_BEDROCK=1 and pinned ANTHROPIC_DEFAULT_*_MODEL in env, SSO with awsAuthRefresh, dedicated AWS account, minimal IAM. Deny Read(./.env), Read(./secrets/**) and risky Bash; disableBypassPermissionsMode: "disable"; allowManagedPermissionRulesOnly and allowManagedHooksOnly with org PreToolUse hooks (exit 2) for force-push and similar. Sandbox enforced (enabled, failIfUnavailable, allowUnsandboxedCommands: false, narrow allowedDomains, denyRead for credentials). MCP: allowedMcpServers by serverUrl/serverCommand + allowManagedMcpServersOnly (or managed-mcp.json for a fixed set). Plugins: strictKnownMarketplaces = internal marketplace, disableSideloadFlags. Telemetry: CLAUDE_CODE_ENABLE_TELEMETRY=1, OTLP endpoint, OTEL_RESOURCE_ATTRIBUTES with team.id/cost_center; prompts stay redacted. Managed CLAUDE.md for org-wide guidance.

Repo: short CLAUDE.md, path-scoped rules, .claude/settings.json with team allow rules and enabledPlugins, .mcp.json for approved shared servers using ${VAR} secrets. User: personal preferences only. CI: claude-code-action@v1 in automation mode with OIDC to Bedrock (use_bedrock, id-token: write), claude_args with narrow --allowedTools, an explicit --permission-mode dontAsk and --max-turns; job timeout, concurrency group. Pilot with a small cohort, watch OTel and /doctor reports, then widen. Managed settings; Sandboxing; Managed MCP; Bedrock; GitHub Actions; Monitoring.

  • Security controls live in managed settings, not repo or user files
  • Secrets blocked by Read deny rules plus sandbox, not .claudeignore or CLAUDE.md
  • Bypass mode disabled; hooks for must-never commands, with exit 2
  • MCP allowlist by URL/command (or managed-mcp.json); marketplace allowlist
  • Bedrock with pinned models, SSO, least-privilege IAM
  • OTel via managed env with team attributes, prompts redacted
  • CI: OIDC, no personal tokens, scoped tools or --bare, turn/time/concurrency limits
  • Phased rollout with a pilot and measurement
