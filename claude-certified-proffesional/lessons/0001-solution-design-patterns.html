Solution design & architecture patterns

The exam's favourite move: give a business problem, ask for the simplest pattern that solves it.

≈ 18 minutes 1 recall + 13 questions + 1 scenario D1

How the real exam asks. 63 scenario items in 120 min (≈ 1 min 54 s each). Some are multiple response: the item says how many to pick. Pass = scaled 720/1000. Exam guide §5. This lesson's questions copy that style.

1 · Recall first

Without looking: (a) What separates a workflow from an agent? (b) What is the augmented LLM? (c) Name the five workflow patterns from Anthropic's "Building effective agents", with a one-line "use when" each.

(a) Workflow: LLMs and tools orchestrated through predefined code paths. Agent: the LLM dynamically directs its own process and tool use.
(b) An LLM enhanced with retrieval, tools, and memory, the building block of every agentic system.
(c) Prompt chaining: fixed sequential steps; trade latency for accuracy. Routing: classify input, send to a specialised handler. Parallelization: independent subtasks (sectioning) or same task many times (voting). Orchestrator-workers: subtasks not known in advance; a lead decides them per input. Evaluator-optimizer: generate → critique loop when criteria are clear and iteration measurably helps.

  • Predefined code paths vs model-directed control
  • Augmented LLM = retrieval + tools + memory
  • Named at least 4 of the 5 patterns
  • Correct "use when" for orchestrator-workers vs prompt chaining

2 · The ideas that matter

Start simple, add complexity only when it pays. Anthropic's core advice: find "the simplest solution possible, and only increasing complexity when needed". Often a single augmented-LLM call with retrieval and good examples is enough. Building effective agents. On the exam, the over-engineered option (autonomous multi-agent for a fixed 3-step task) is a classic distractor.

Pick by predictability. If you can write the steps down in advance, use a workflow: cheaper, faster, testable. Use an agent for open-ended problems where "it's difficult or impossible to predict the required number of steps". Agents cost more and risk compounding errors, so they need sandboxed testing, guardrails and stopping conditions (e.g. max iterations). Ibid.

Where you build it (current platform options). The patterns don't depend on the platform, but the scenario often decides it. Messages API / Client SDK: you write the tool loop yourself (or use the beta tool runner); you get full control. Claude Agent SDK (formerly Claude Code SDK): Claude Code's agent loop, tools, hooks, subagents and permissions as a Python/TypeScript library, running in a process you operate. Claude Managed Agents (beta): Anthropic hosts the harness and the sandbox, for long-running and asynchronous work. It is not currently eligible for ZDR or a HIPAA BAA. Claude Code CLI: interactive and one-off developer work. Agent SDK overview; Managed Agents overview. "Building effective agents" (Dec 2024) is still the source for the pattern vocabulary. Its own note says the tooling has changed since then and points to Managed Agents. Building effective agents.

Multi-agent is a cost decision, and usually the wrong one. Anthropic's current guidance (Jan 2026) is that most teams don't need it: single agents handle most work, and multi-agent typically uses 3–10× the tokens of a single agent for the same task. It pays off in three cases: context pollution is hurting performance, tasks can run in parallel, or specialization improves tool selection or focus. It fits badly with tightly coupled components and with sequential phases of the same work. When to use multi-agent systems. The best-known data point is historical. In June 2025, Anthropic's research system (Claude Opus 4 lead + Claude Sonnet 4 subagents) beat single-agent Opus 4 by 90.2% on an internal eval, using ~15× the tokens of chat (~4× for a single agent). The same post lists shared-context and many-dependency domains, and most coding tasks, as poor fits. Multi-agent research system.

Decomposition: split by context, not by job title. Split work where the context separates, not by problem phase. A planner → coder → tester chain is a lossy "telephone game"; "an agent handling a feature should also handle its tests". A dedicated verification subagent works well, but watch for the "early victory" problem: outputs marked as passing without thorough testing. Ibid. Each delegated task needs an objective, output format, tool and source guidance, and clear boundaries; vague tasks caused duplicated work. Scale effort to complexity (a simple fact-find is 1 agent / 3–10 tool calls). Subagents return a condensed summary (often 1,000–2,000 tokens), which keeps the lead's context clean. Multi-agent research system; Context engineering.

Orchestration options on the platform today. Managed Agents offers three modes. Subagents: the agent delegates and can follow up with each one; delegation is one level deep. Dynamic workflows: the agent writes a program that runs many agents in phases and merges their results; the docs recommend it for most multi-agent work (audits, migrations, deep research). Advisor: one agent does the work and consults a stronger model at key moments (escalation). Cap spend with a session budget. Multiagent orchestration. For agents that run across many context windows, give them an initializer session, a progress file plus git history, and a feature list worked one feature at a time. Long-running agent harnesses (Nov 2025).

End-to-end means closing the loop. The blueprint frames architecture as input → processing → output → feedback loops. The feedback leg (user corrections, outcomes, human review results) feeds the eval set and the next prompt or retrieval iteration. Without it you can't prove improvement. Exam guide §6, D1.

Start from business value, not the model. The blueprint names value pillars: efficiency, transformation, productivity, cost, performance SLAs. Translate the problem into a measurable target (handle time, cost per ticket, p95 latency) before picking a pattern. Exam guide §6. 3 · Practice

An insurer receives claim emails in four known categories, each needing a different handling prompt and tool set. Most emails are simple; a few are complex. Which design best fits?

  1. A classifier routes each email to a category-specific handler
  2. An orchestrator spawns dynamic workers for every incoming email
  3. An evaluator-optimizer loop rewrites each email until it's approved
  4. One autonomous agent holds every tool for all categories
Routing. Distinct, known categories handled better separately. It also lets simple emails go to a cheaper, faster model. Orchestrator-workers is for subtasks you can't know in advance. One agent with every tool is tool bloat plus needless autonomy. Building effective agents.

A finance team wants an "autonomous agent" to produce a monthly report. Every month it's the same four steps: pull figures, compute variances, draft commentary, format. What do you recommend?

  1. A prompt chain with programmatic checks between fixed steps
  2. A multi-agent system with one subagent assigned per step
  3. An autonomous agent with a high maximum iteration limit
  4. An orchestrator that decides the steps fresh every month
Steps are known in advance, so a workflow (prompt chaining) is simpler, cheaper, and testable. Gates between steps (e.g. "do the variances sum?") catch errors early. Autonomy buys nothing here and adds cost and compounding-error risk. A subagent per step is the "sequential phases" anti-pattern; an orchestrator re-deciding known steps is needless. Building effective agents; When to use multi-agent systems.

A coding assistant must implement a feature request. The files that need changing depend entirely on the request. Which pattern fits?

  1. Orchestrator-workers, with subtasks decided by the lead per request
  2. Prompt chaining, with a fixed sequence of file edits
  3. Parallelization by voting, with every file edited three times
  4. Routing, with one specialist handler assigned per repository file
Orchestrator-workers: "subtasks aren't pre-defined, but determined by the orchestrator based on the specific input". Anthropic's own example is multi-file coding changes. Ibid.

Three independent prompts review the same contract for risky clauses. A clause is flagged when at least two agree. This is…

  1. Parallelization: voting
  2. Parallelization: sectioning
  3. Evaluator-optimizer loop
  4. Orchestrator-workers pattern
Voting: the same task several times to get diverse outputs and higher confidence. Sectioning splits different independent subtasks, e.g. a guardrail screen running alongside the main answer. Evaluator-optimizer is a generate-critique loop, not independent votes; orchestrator-workers decides subtasks at run time. Building effective agents.

A translation service has clear quality criteria (terminology list, tone guide), and human reviewers report that a second pass with feedback reliably improves drafts. Which pattern adds the most value?

  1. Evaluator-optimizer: one call drafts, another critiques in a loop
  2. Routing: send each document to a translator by length
  3. Sectioning: split each document and translate parts in parallel
  4. Autonomous agent: let the model choose its own process
The two preconditions for evaluator-optimizer are met: clear evaluation criteria, and iteration that measurably helps. Literary translation is Anthropic's example. Ibid.

For which two workloads is a multi-agent (orchestrator + parallel subagents) design a poor fit?

  1. Tightly interdependent tasks where every agent needs the same shared context
  2. A typical coding task with few genuinely parallelisable subtasks inside it
  3. Broad research across many independent directions at once, with high value
  4. Gathering information that far exceeds what fits in one context window
Anthropic lists shared-context / many-dependency domains and most coding tasks as poor fits; the Jan 2026 guidance adds tightly coupled components. Parallel, breadth-first research and information beyond one window are exactly where multi-agent shines (parallelism and protecting context are two of its three good-fit cases). Multi-agent research system; When to use multi-agent systems.

A sponsor asks why the multi-agent prototype's bill is so much higher than the single-agent version's. Per Anthropic's current guidance, multi-agent typically uses roughly how many times the tokens of a single agent for the same task?

  1. About 3–10×
  2. About 1–2×
  3. About 20–40×
  4. About 50–100×
3–10× a single agent (Jan 2026). 1–2× understates the cost; 20× and above overstates it. Don't confuse this with the June 2025 research-system figures, which compare against chat: ~4× for one agent, ~15× for multi-agent. The architect's answer: multi-agent only makes sense where the task's value pays for it. When to use multi-agent systems; Multi-agent research system.

Your orchestrator's subagents keep duplicating each other's searches. Which two additions to each delegated task description most directly fix this?

  1. A specific objective, with clear boundaries from the other subagents
  2. The exact output format that the lead agent expects back
  3. The lead agent's entire conversation history, copied in full verbatim
  4. An instruction to make as many tool calls as possible
Anthropic fixed duplicated work by giving each subagent an objective, output format, guidance on tools and sources, and clear task boundaries. Dumping the full history bloats the subagent's context. "As many calls as possible" makes the duplication worse. Ibid.

Why should subagents return a condensed summary (often 1–2k tokens) to the lead instead of their full working transcript?

  1. It keeps the lead's limited context focused on what matters
  2. The API forbids passing long transcripts between two separate agents
  3. Summaries are the only thing that makes subagent outputs cacheable
  4. Full transcripts would force the lead onto a smaller model
Context is a finite attention budget; recall degrades as it fills ("context rot"). Subagents explore deeply in their own clean context and hand back only the distilled result. The other options are invented: no API rule bans long transcripts, caching isn't tied to summaries, and transcript length doesn't dictate the lead's model. Context engineering.

A team built a planner agent, then a coder agent, then a tester agent, each handing off to the next. Bugs get lost between handoffs, and the tester keeps reporting "all pass" too early. What is the best redesign?

  1. One agent owns each feature and its tests; add a separate verification agent
  2. Add a fourth reviewer agent between the coder and tester in the chain
  3. Pass every agent's full transcript forward so that no context is ever lost
  4. Move all three agents to the most capable model to reduce handoff errors
This is problem-centric decomposition (sequential phases of the same work), a lossy "telephone game". Split by context instead: "an agent handling a feature should also handle its tests". A dedicated verification subagent addresses the "early victory" problem. Another handoff adds one more lossy hop. Full transcripts cause context pollution. A bigger model doesn't fix a bad split. When to use multi-agent systems.

A client wants an agent that runs for hours on document migrations in a sandbox, with scheduled runs. They don't want to build or host the agent loop, sandbox or tool execution. No regulated health data is involved. Which option fits best?

  1. Claude Managed Agents, with the harness and the sandbox hosted by Anthropic
  2. The Messages API, with a custom tool loop written and hosted in-house
  3. The Claude Agent SDK, embedded in a service the client operates itself
  4. The Claude Code CLI, run interactively by an engineer during each migration
Managed Agents is the hosted harness, built for long-running, asynchronous and scheduled work, with no loop or sandbox to build. The Messages API means writing your own loop. The Agent SDK runs in a process you operate. The CLI is for interactive developer use. Caveat: Managed Agents is in beta and not currently eligible for ZDR or a HIPAA BAA, so regulated health data would change the answer. Managed Agents overview; Agent SDK overview.

A retail client says, "We want to use Claude for customer service." What should the architect establish first?

  1. The measurable business outcome, like handle time or cost per contact
  2. The most capable Claude model available, so quality is never limited
  3. A multi-agent prototype, so stakeholders can see what is really possible
  4. The specific vector database product the solution will be built around
Translate the business problem first: which value pillar (efficiency, cost, SLA…) and which metric proves success. Model, pattern and tooling follow from that. Starting from technology (top model, multi-agent demo, a vector DB) is the classic wrong answer in D1 and D6. Exam guide §6, D1.

A support-drafting system is live. Agents edit Claude's drafts before sending, but nobody captures those edits. Which part of the end-to-end architecture is missing?

  1. The feedback loop that turns edits into eval data and improvements
  2. The input stage that normalises tickets before they reach the model
  3. The processing stage that selects the correct tools for each ticket
  4. The output stage that formats drafts for the support agents' interface
Input → processing → output → feedback loop. Human edits are free, high-quality signal: diff them to build eval cases and find prompt or retrieval gaps. Without that loop, the system can't measurably improve. Exam guide §6.

4 · Architect scenario

Hollis Freight, a mid-size logistics company, gets 40k customer emails a month. Roughly 60% are "where's my shipment?" (answerable from the tracking API), 25% are quote requests (pricing API plus business rules), and 15% are damage claims. Claims need evidence gathering across photos, delivery logs and driver notes, and can end in payouts up to $5k. The COO cares about two things: cost per email (now $4.10 with human agents) and a 4-hour first-response SLA that they currently miss 30% of the time.

(8 min) Sketch the architecture. (a) Which pattern for the overall flow and for each email type, and why? (b) Where, if anywhere, is an agent justified? (c) How do you close the feedback loop? (d) Which value pillars and metrics do you report to the COO?

(a) Routing at the front: a fast, cheap model classifies each email into three known categories. Status: a single augmented-LLM call with a tracking-lookup tool; no agent needed. Quotes: a prompt chain: extract fields → call pricing API → apply rules in code → draft, with a programmatic gate that the quoted price matches the API.
(b) Claims are the only open-ended path. Evidence gathering varies per case, so an agent (or orchestrator-workers over the evidence sources) is defensible. It needs a max-iteration stop, read-only tools, and human approval before any payout: high-impact, irreversible action. Build it single-agent first; add subagents only if evidence-gathering context starts polluting the main one. Host it on the Agent SDK in your own service, or on Managed Agents if you'd rather not run the loop and sandbox yourself.
(c) Log every human edit, override and claim decision. Turn them into eval cases. Review weekly and iterate on prompts and retrieval. Track the reclassification rate on routing.
(d) Cost: cost per email vs $4.10. Performance SLA: % first responses within 4 h. Efficiency: automation or deflection rate and handle time. Optionally quality: CSAT and claim-decision accuracy vs human baseline.

  • Routing front door on a small model; known categories
  • Workflows (single call / chain) for status and quotes, not agents
  • Agent only for claims, bounded (stop condition, limited tools)
  • Human-in-the-loop before payouts
  • Feedback loop: human edits/decisions → eval set → iteration
  • Metrics tied to the COO's pillars: cost per email and SLA %
