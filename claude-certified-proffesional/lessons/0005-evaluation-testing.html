0 · Spaced review

A law firm's client intake is always the same three steps: extract the parties, check the conflicts database, draft the engagement letter. Which design fits best?

  1. A prompt chain with a programmatic check between fixed steps
  2. An autonomous agent that plans its own steps every time
  3. An orchestrator that spawns fresh new workers for every intake
  4. A voting setup that runs each intake three separate times
Steps known in advance → workflow (prompt chaining) with gates. Agents and orchestrators are for subtasks you can't predict; voting is for confidence on one task, not sequencing. Building effective agents.

An app caches a long system prompt, but the usage logs show cache_read_input_tokens stays at 0. The team recently added the current timestamp to the top of the system prompt. What is the most likely cause?

  1. The changing timestamp breaks the exact prefix match every request
  2. Cache reads are only reported on the Message Batches API
  3. The cache only covers messages, never the system prompt itself
  4. Cache entries always expire before a second request can arrive
Cache hits need 100% identical prefix segments, in order tools → system → messages. A value that changes per request at the top of the prompt means every request is a miss. Put dynamic content after the cached static prefix. Reads are reported on normal requests too, and the 5-minute TTL refreshes on each hit. To find the break without guessing, turn on cache diagnostics: pass the previous response's id and the API reports where the prefix diverged (model, system, tools or messages). Prompt caching; Cache diagnostics.

In Anthropic's contextual retrieval experiments, which combination produced the largest reduction in failed retrievals (1 − recall@20)?

  1. Contextual embeddings with BM25, plus a reranking step
  2. Contextual embeddings on their own, with no reranking
  3. Plain embeddings with a larger number of chunks
  4. Contextual BM25 on its own, with no embeddings
Embeddings alone: −35%. Embeddings + BM25: −49%. Plus reranking: −67% (5.7% → 1.9%). For knowledge bases under ~200k tokens, skip RAG and put the whole thing in the prompt with caching. Contextual retrieval.

1 · Recall first

Without looking: (a) What four properties make a success criterion good? (b) Name the three grader types, with one strength and one weakness each. (c) Define pass@k and pass^k. Which one matters for a customer-facing agent? (d) Capability eval vs regression eval: what pass rate do you expect from each?

(a) Specific, measurable, achievable, relevant. Usually several dimensions at once (accuracy, latency, cost, safety…).
(b) Code-based: fast, cheap, objective, reproducible; brittle and lacks nuance. LLM-as-judge: flexible, scalable, handles open-ended output; non-deterministic, costlier than code, and needs calibration against humans. Human: gold standard; slow, expensive, hard to scale.
(c) pass@k: probability at least one of k trials succeeds (rises with k). pass^k: probability all k succeed (falls with k). Customer-facing agents need consistency, so pass^k.
(d) Capability: starts low, gives the team a target. Regression: near 100%, protects what already works. Capability tasks "graduate" into the regression suite.

  • SMAR(T)-style criteria: specific, measurable, achievable, relevant
  • Three grader types with a correct trade-off each
  • pass@k = at least one; pass^k = all k
  • pass^k for customer-facing reliability
  • Capability low / regression ≈ 100%

2 · The ideas that matter

Success criteria come first, and they're numbers. Good criteria are specific, measurable, achievable, relevant. "Safe outputs" is bad; "less than 0.1% of 10,000 outputs flagged for toxicity" is good. Most use cases need several dimensions at once: task fidelity, consistency, relevance, tone, privacy, context use, latency and price. Anthropic's example pairs F1 ≥ 0.85, 99.5% non-toxic and 95% of responses under 200 ms. Define success criteria and build evaluations. The blueprint's five metrics (accuracy, latency, cost, safety, security) map straight onto these. Security is measured the same way, e.g. a pass rate on prompt-injection or data-leak test cases.

Design evals that mirror real traffic, then automate. Three principles: be task-specific (include edge cases), automate grading where possible, and prefer volume: "more questions with slightly lower signal automated grading is better than fewer questions with high-quality human hand-graded evals." Edge cases to include: irrelevant or missing input, overly long input, harmful input, and ambiguous cases where even humans disagree. Claude can help generate more cases from a seed set. Where the cases come from. A golden set (inputs with reference answers), deliberate edge cases, and production-sampled cases: "20–50 simple tasks drawn from real failures is a great start". Convert bug reports and support tickets into tasks. Balance them: test where a behaviour should happen and where it shouldn't, or you'll get an over-triggering agent. Demystifying evals. Anthropic's research team started with about 20 real queries, because early changes have big effects (30% → 80% from one prompt tweak). Multi-agent research system.

Agent evals: the vocabulary. Task = one test with inputs and success criteria. Trial = one attempt; run several because outputs vary. Transcript = the full record (tool calls, reasoning). Outcome = the final environment state, e.g. "does the reservation exist in the DB", not "did the agent say it booked". Grade what the agent produced, not the path it took: exact tool-sequence checks reject valid routes. Use partial credit for multi-part tasks and start each trial from a clean environment. Capability vs regression. Capability evals ask "what can it do?" and should start at a low pass rate. Regression evals ask "does it still do what it did?" and should sit near 100%. Passing capability tasks graduate into the regression suite. A 0% pass rate across many trials usually means a broken task, so check each task with a reference solution. Read the transcripts: Opus 4.5 first scored 42% on CORE-Bench; after fixing grader and spec bugs (e.g. rigid grading that rejected "96.12") and loosening the scaffold, it scored 95%. Ibid.

Offline first, then online, then watch (Swiss cheese). No single layer catches everything. Automated evals are reproducible and run on every commit, but give false confidence if they don't match real usage. A/B tests measure real outcomes and control for confounds, but are slow: "days or weeks to reach significance". Production monitoring is ground truth but reactive. User feedback is sparse and self-selected. Manual transcript review catches subtle issues but doesn't scale. Ibid. For long-running agents, Anthropic shifts traffic gradually with rainbow deployments. Multi-agent research system. For a model or cost change, Anthropic's method ends: "run the winner in shadow on a traffic slice before cutover, then keep the suite running". Optimizing for cost and intelligence. Change one variable at a time (prompt, model, effort or retrieval) so you can attribute any movement. General experimentation practice; no single Anthropic doc prescribes it.

Is the difference real? An eval score is a sample estimate. Report the standard error of the mean (95% CI ≈ mean ± 1.96 × SEM). Cluster the standard errors when questions come in groups (they can be over 3× naive SEs). Resample each question several times to cut noise. Compare two prompts or models with a paired-differences test on the same questions. Use power analysis to size the eval before running it. A statistical approach to model evals. For agent evals, the environment adds noise too: resource settings alone moved a Terminal-Bench 2.0 score by 6 points, so treat gaps under ~3 points with suspicion until configs match, and run on several days. Quantifying infrastructure noise in agentic coding evals.

Reducing hallucination. The basics: let Claude say "I don't know"; for long docs (over 20k tokens), extract word-for-word quotes first and answer only from them; make every claim cite a quote, and retract any claim without one. Advanced: review the summarized thinking when an answer looks wrong, run best-of-N and compare (inconsistency is a hallucination signal), iterate on the output, and restrict Claude to the provided documents. These techniques reduce hallucination but don't eliminate it, so validate high-stakes output. Reduce hallucinations.

Optimize cost, tokens and latency

Get the prompt working first, then optimise. Cutting latency too early "might prevent you from discovering what top performance looks like". Reduce latency. Anthropic sorts cost levers into two kinds. Free wins cut spend without touching quality: caching, token trimming, batch, a prompt audit, and workspace spend limits as the backstop. Trade-offs swap cost for intelligence: model choice, effort, output caps and task budgets, multi-model designs. Caching was the largest lever by far in their measurements (agent-loop cost cut 2.7–5.3×). Compare models on cost per completed task, not per token: a stronger model often finishes in fewer turns, so its higher token price can still win (but not always, so measure). 3 · Practice

A product owner writes the success criterion "the summariser should be accurate and fast". Which rewrite best follows Anthropic's guidance?

  1. 90% of 500 held-out summaries pass the accuracy rubric; p95 under 3s
  2. All summaries should be accurate, readable, and much faster than they are
  3. Reviewers should feel satisfied with summary quality and speed after the pilot
  4. The summariser should match top model quality at the lowest possible cost
Good criteria are specific, measurable, achievable, relevant, and usually cover several dimensions (here accuracy and latency) on a defined test set. The others are vague ("much faster", "satisfied", "top model quality") with no test set or threshold. Define success criteria and build evaluations.

An intent classifier assigns each support message one of 14 labels. You have 3,000 human-labelled messages. Which grading method should the eval use?

  1. Code-based exact match of predicted label against the human label
  2. LLM judge rating every predicted label on a one-to-five scale
  3. Human reviewers re-checking each prediction by reading the full message
  4. Embedding similarity between the predicted label and the message text
Pick the "fastest, most reliable, most scalable" grader. With gold labels, exact match is the answer. An LLM judge adds cost and non-determinism for no gain. Human grading is slow ("avoid if possible"). Similarity to the message text doesn't measure correctness. Develop tests.

You will grade the tone of 2,000 customer-service replies with an LLM judge. Which two practices most improve the judge's reliability? (Choose two.)

  1. A detailed rubric with an explicit, constrained output like a 1–5 score
  2. First calibrating the judge's grades against a sample graded by human experts
  3. Asking for a long open-ended qualitative critique instead of any numeric score
  4. Running the judge only on the replies that customers already rated poorly
Docs: use detailed, clear rubrics and empirical output (correct/incorrect or 1–5), and run the grader with thinking on so it reasons before scoring. The agent-evals post: calibrate LLM judges against human experts, and give the judge an "Unknown" option. Purely qualitative critiques are "hard to assess quickly and at scale". Grading only poorly-rated replies is a biased, one-sided sample. Develop tests; Demystifying evals.

A customer-facing booking agent succeeds on 80% of trials for a task. Customers expect it to work every time. Over three independent trials, what is pass^3?

  1. About 51%: all three succeed only half the time
  2. About 99%: at least one of three attempts succeeds
  3. About 80%: the rate stays fixed as k grows
  4. About 24%: three times the twenty percent failure rate
pass^k = p^k = 0.8³ ≈ 0.51: the chance that all k trials succeed. 99% is pass@3 (at least one success, 1 − 0.2³), the right metric only when one success is enough. For customer-facing reliability, pass^k is the honest number. Demystifying evals.

A team builds an eval suite for multi-step refund handling, a capability the agent doesn't have yet. It passes 12% today, and every task has a verified reference solution. A colleague says the suite is broken and should be dropped. Best response?

  1. Keep it: a capability eval should start low and give a target
  2. Drop it: any eval suite under 90% means the graders are broken
  3. Merge it into the regression suite so it runs on every commit
  4. Replace it with easier tasks until the pass rate exceeds 80 percent
Capability evals start low; regression evals sit near 100%. Merging a 12% suite into regression would make that suite permanently red. Tasks graduate into regression only once they pass reliably. A 0% rate across many trials would point to a broken task, but these tasks have reference solutions. Demystifying evals.

An airline-rebooking agent's eval fails many trials because the grader requires an exact sequence of tool calls. Reading the transcripts, you see the agent often reaches a correct rebooking by a different route. What should change?

  1. Grade the final reservation state in the database, not the path
  2. Add prompt instructions forcing the agent to follow the expected sequence
  3. Switch to a larger model that follows tool orderings more reliably
  4. Lower the pass threshold so partial sequence matches count as passes
"Grade what the agent produced, not the path it took." Check the outcome (end state). Rigid sequence checks reject valid strategies the designers didn't anticipate. This is a grader bug, not an agent bug, so prompt or model changes treat the wrong thing. Demystifying evals; Multi-agent research system (end-state evaluation).

An HR policy assistant (RAG) gives a wrong parental-leave answer. The trace shows the correct, current policy paragraph was in the retrieved chunks, but the answer states a different number of weeks. Most likely failure and first fix?

  1. Hallucination; have it quote retrieved text before it answers
  2. Retrieval failure; re-index the corpus and tune chunk size
  3. Model mismatch; move every query to the largest model
  4. Stale index; schedule a full document refresh every night
The right context was present, so retrieval did its job and generation went wrong. Ground it: quote first, answer only from the quotes, cite and verify, restrict Claude to the provided docs. Contrast with official sample 3, where the right chunks were missing after a refresh, which points to retrieval. Jumping to the biggest model skips the diagnosis. Reduce hallucinations; Exam guide §8.

A due-diligence tool summarises 80-page contracts, and reviewers find occasional invented clauses. Which two prompt changes does Anthropic recommend to reduce this? (Choose two.)

  1. Permit the model to say it lacks enough information to answer
  2. Extract word-for-word quotes first, then base the analysis only on them
  3. Encourage the model to fill gaps using its broad general knowledge
  4. Ask for a single long answer with no follow-up verification step
Basic techniques: allow "I don't know" and use direct quotes for grounding on long documents (over 20k tokens). The docs say the opposite of the distractors: restrict Claude to the provided documents, and verify with citations, best-of-N or iterative refinement. Reduce hallucinations.

Prompt B scores 83% and prompt A 80% on the same 150-question eval. A stakeholder wants to ship B today. Which two analyses should you run before claiming B is better? (Choose two.)

  1. A paired-differences test on each question's scores for both
  2. Confidence intervals from the standard error of each mean
  3. A rerun covering only the questions that A failed
  4. A comparison of average output length between both prompts
Report the SEM / 95% CI with every score. When both variants answer the same questions, use a paired-differences analysis: it removes question-difficulty variance and shrinks the error. Use power analysis to check whether 150 questions can detect a 3-point gap at all. Rerunning only A's failures is biased (regression to the mean), and output length isn't quality. Statistical approach to model evals.

Every night an insurer classifies about 200,000 claim notes. Each request shares the same 6,000-token instruction block, and results are needed by 8 a.m. Which two changes cut cost most without hurting accuracy? (Choose two.)

  1. Submit the nightly job through the Message Batches API
  2. Cache the shared instruction prefix, using the one-hour TTL
  3. Truncate the instruction block to its first 1,000 tokens
  4. Raise the effort level so fewer requests need retries
Batch: 50% off input and output; most batches finish in under 1 h (24 h max), which fits overnight. Caching stacks with the batch discount; reads cost 0.1× base input (0.05× on Opus 5.5 and Sonnet 5.5), and the docs suggest the 1-h TTL because batches can take longer than 5 minutes. Truncating drops needed policy (the official sample 2 distractor). Higher effort adds tokens. Batch processing; Pricing.

Users of an internal chat assistant say they stare at a blank screen for several seconds before anything appears. Total generation time is acceptable. Most direct fix?

  1. Stream responses so the first tokens appear right away
  2. Move the whole workload to the Message Batches API
  3. Enable fast mode for higher output tokens per second
  4. Add several more few-shot examples to the system prompt
The complaint is perceived latency, i.e. time to first token. Streaming shows output as it's generated. Batch is async (minutes to hours). Fast mode raises output tokens per second, "not time to first token", and costs a premium, while total time is already fine. More examples add prompt tokens, which can add latency. Reduce latency; Fast mode.

A contract-risk agent runs on Haiku. On the eval, multi-step reasoning cases fail across five prompt revisions, and the same cases pass on Opus. Simple extraction cases pass on both. Best architectural response?

  1. Route the complex reasoning cases to the stronger model only
  2. Keep rewriting the prompt until the small model passes everything
  3. Send every case, simple or complex, to the stronger model
  4. Add retrieval of more documents for the failing reasoning cases
Failures that survive prompt variants but disappear on a stronger model point to model mismatch on that slice. Route (tiering): easy cases stay cheap, hard ones escalate. Moving everything wastes money on cases Haiku already passes. Also try raising effort, which is "often a better lever than switching models", or let Haiku consult a stronger model through the advisor tool. Nothing suggests missing context. Choosing a model; Advisor tool; Building effective agents (routing).

A team picks a mid-tier model over a frontier model for its coding agent because the frontier model's price per token is five times higher. Which measure should decide the choice?

  1. Cost per completed task, measured on the team's own eval
  2. List price per million output tokens from the pricing page
  3. Average input tokens per request across a full day's traffic
  4. Public leaderboard score divided by each model's list token price
"Compare models on cost per completed task", not per token. A stronger model often needs fewer turns, less searching and less backtracking. In Anthropic's runs, Fable 5.1 at low solved 11 more points of tasks than Sonnet 5 for 35% less per solved task, despite a 5× token price. It doesn't always win, so measure on your own tasks. List price and tokens per request ignore whether the task got done. Leaderboards aren't your workload. Optimizing for cost and intelligence.

4 · Architect scenario

Calder Mutual, a health insurer, runs a member-benefits assistant: RAG over 3,000 policy documents on a mid-tier model, about 1.2M questions a month. The CFO wants a 40% cost cut, and an engineer proposes "just switch everything to Haiku". Compliance has one red line: the assistant must never state coverage that isn't in the policy. Last month, right after the quarterly policy refresh, complaints about wrong answers doubled. There is no eval suite today. Logs keep request and response text, but not retrieved chunks or token usage.

(8 min) (a) Write 3–4 success criteria covering accuracy, safety, latency and cost. (b) Design the eval set and graders. (c) How do you investigate the complaint spike? (d) How do you hit the cost target, and how do you decide on Haiku and roll it out?

(a) E.g. ≥ 95% of golden-set answers judged correct; 0 unsupported coverage claims on a 500-case faithfulness set (each claim must cite a retrieved passage); p95 TTFT under 2 s; cost per answer −40% vs baseline. Specific, measurable, on a named test set.
(b) Start with ~50 real failures from the complaint queue, then grow. Golden set with reference answers from benefits experts. Edge cases: missing info, out-of-scope, ambiguous, and very long member messages. Balanced "should answer" and "should decline" cases. Graders: code for citation presence and format; an LLM judge with a rubric (correctness, faithfulness to quotes, "Unknown" allowed), calibrated against expert human labels; a small human spot-check each release. A separate retrieval eval (recall@k).
(c) It started at the refresh, so suspect retrieval/indexing first (sample 3). Add tracing of retrieved chunks. For failing cases, check whether the right passage was retrieved. If not, it's retrieval (re-index, chunking, hybrid + rerank). If it was, it's hallucination (quote-first, cite-and-verify, "I don't know"). Turn every confirmed failure into a regression case.
(d) Free wins first: cache the static system prompt and policy preamble, trim unneeded tokens and output length, and batch any offline jobs (e.g. nightly summaries). Then trade-offs: sweep effort down on the current model. For Haiku: run the same eval on both models, compare cost per correct answer (not per token; note Haiku 5.5's higher rate for prompts over 100k tokens), report CIs and a paired-differences comparison, and check the faithfulness red line per slice. Likely result: route simple FAQs to Haiku and escalate complex cases. Then run the winner in shadow on a traffic slice and roll out one change at a time, while monitoring cost per answer (usage fields plus the Usage & Cost API), cache-read share and complaint rate.

  • Measurable multi-dimensional criteria incl. a hard safety threshold
  • Eval set seeded from real failures + golden + edge + balanced cases
  • Mixed graders; LLM judge calibrated against humans
  • Retrieval checked first for the post-refresh spike; trace retrieved chunks
  • Distinguishes retrieval failure from hallucination with evidence
  • Caching / effort / output length before or alongside model change
  • Model switch decided by paired eval + CIs on cost per correct answer; routing rather than all-or-nothing
  • Staged rollout, one change at a time, with monitoring feeding the eval set
