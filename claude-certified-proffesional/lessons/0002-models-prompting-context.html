Models, prompting & context engineering

Pick the smallest model and effort that pass your evals. Then put the right tokens, in the right order, into a context you treat as a scarce budget.

≈ 19 minutes 3 review + 1 recall + 13 questions + 1 scenario D2 D1 review

Current as of Oct 2026. Model names, prices, limits and feature status below match the Claude docs as checked on 2026-10-12. Models overview.

0 · Spaced review

A bank's onboarding assistant runs the same five checks for every applicant, with a compliance gate after the third check. Which design fits best?

  1. A prompt chain with a programmatic gate after step three
  2. An autonomous agent that plans the checks for each applicant
  3. An orchestrator that spawns a fresh worker per applicant check
  4. A voting ensemble that runs every check three separate times
Steps are known in advance, so a workflow (prompt chaining with gates) beats autonomy: cheaper, testable, no compounding-error risk. Orchestrator-workers is for subtasks you can't predict. Voting buys confidence, not a gate. Building effective agents.

A sponsor wants a multi-agent system for a refactoring task where every step depends on the previous edit. What is the best response?

  1. Use a single agent, since tightly dependent steps suit multi-agent poorly
  2. Use multi-agent, since parallel subagents will always outperform a single agent
  3. Use multi-agent, but copy the lead's full history into every subagent
  4. Use voting, since three agents agreeing makes each code edit safer
Anthropic names shared-context, many-dependency work and most coding as poor fits for multi-agent, which also costs ~15× chat tokens. Copying full history into subagents defeats the point of clean contexts. Multi-agent research system.

A lead agent delegates "research competitors" to five subagents, and their results overlap heavily. What is the most direct fix?

  1. Give each subagent a distinct objective, boundaries and output format
  2. Increase the number of subagents so coverage becomes more complete
  3. Switch every subagent to the largest model at maximum effort
  4. Pass every subagent the complete conversation history of the lead
Duplicated work came from vague delegation. The fix is a task spec: objective, output format, tool guidance, boundaries. More agents or bigger models multiply the overlap. Ibid.

1 · Recall first

Without looking: (a) Name the four current general-availability Claude models from most to least capable, with a "use when" each. (b) What is effort, and why is it often a better lever than switching model? (c) Give the prompt-cache prefix order, the write/read multipliers, and what breaks a cache hit. (d) What are the three levels of Agent Skills progressive disclosure?

(a) Fable 5.1: demanding reasoning, long-horizon agentic work. Opus 5.5: the default starting point; long-running agentic coding and knowledge work. Sonnet 5.5: best speed and intelligence balance. Haiku 5.5: high-volume, latency-sensitive classification, extraction, routing, subagents. All have a 1M context window and 128k max output.
(b) output_config.effort (low → medium → high → xhigh → max) controls how many tokens Claude spends on thinking, tool calls and text, all within one model. The docs say tuning it "is often a better lever than switching models".
(c) tools → system → messages. 5-min write 1.25×, 1-h write 2×, read 0.1× by default (0.05× on Opus 5.5 and Sonnet 5.5, 0.025× on Fable 5.1). A hit needs a 100% identical prefix, so any change invalidates that level and everything after it.
(d) Metadata (name + description, ~100 tokens, always loaded). SKILL.md body (under 5k tokens, loaded when triggered). Resources/scripts (loaded or run only when needed; script code never enters context).

  • Four tiers in order, with a sensible "use when"
  • Effort = token-spend control within one model; tune before switching
  • Prefix order tools → system → messages
  • Write 1.25× / 2×, read ≈ 0.1× (model-specific discounts)
  • Three disclosure levels with rough token costs

2 · The ideas that matter

Model selection: tier, effort, then mode

All four: 1M context, 128k max output, adaptive thinking, text + image input. Haiku's 100k price step counts all input tokens, cache reads and writes included. Models overview; Pricing; Choosing a model.

Two ways to start. Efficiency-first: begin on Haiku and "upgrade only if necessary". Fits prototypes, tight latency, high-volume simple tasks. Capability-first: begin on Opus 5.5, then optimise down by lowering effort or model. Either way, "having a good evaluation set is the most important step". Multi-model designs (a cheap executor escalating to an advisor, or an orchestrator with cheap workers) bill most tokens at the lower rate. Choosing a model.

Effort is the first dial. output_config.effort takes low | medium | high | xhigh | max. It shapes all output tokens: thinking, tool calls and text. Lower effort means fewer, terser tool calls. It's a behavioural signal, not a hard budget. Use max_tokens as the hard cap, because thinking counts toward it. Changing top-level effort between requests breaks the prompt cache. Fable 5.1, Opus 5.5, Sonnet 5.5 and Haiku 5.5 support a per-message effort change (beta) that keeps it. For long agent loops, a task budget (beta, output_config.task_budget) gives Claude an advisory token total for the whole loop; effort tunes depth per step, the budget tunes breadth. Effort; Task budgets.

Thinking: adaptive replaced extended. With adaptive thinking, Claude decides when and how much to think, steered by effort. The old extended thinking (type: "enabled" + budget_tokens) is deprecated on the 4.6 models and returns a 400 error from 4.7 on. Thinking is always on in Fable 5.1 and Opus 5.5, and "disabled" returns a 400 error. Haiku 5.5 can disable it at effort ≤ high. Sonnet 5.5's lowest setting is between_tools. Thinking tokens are billed as output even when hidden (display: "omitted" is the default on these models). Current models also keep earlier turns' thinking blocks in context, so they count toward the window and bill as input on later turns. Thinking; Models overview.

Batch when nobody is waiting. The Message Batches API costs 50% less on input and output. Most batches finish within 1 h, and they expire at 24 h. Limits are 100k requests or 256 MB per batch, and results stay available for 29 days. Discounts stack with caching. For shared context, use the 1-hour cache, because batches can run longer than 5 minutes. Batch processing.

System prompts, templates, guardrails

Clear, direct, motivated. Treat Claude as "a brilliant but new employee who lacks context". Golden rule: if a colleague with minimal context would be confused by the prompt, so will Claude. Explain why a rule exists, not just the rule. A one-sentence role in the system prompt focuses tone and behaviour. Prompting best practices.

Templates = fixed text plus tagged variables. Wrap each kind of content in its own XML tag (<instructions>, <context>, <input>), keep tag names consistent, and nest documents as <documents><document index="n">. For long inputs (20k+ tokens), put the documents at the top and the query at the end. Queries placed at the end improved quality by "up to 30 percent" in tests. Ibid.

Prefill is gone on new models; use structured outputs. From the 4.6 models on, prefilling the last assistant turn returns a 400 error. Migrations: for format, use structured outputs (output_config.format JSON schema) or strict tool use (strict: true). For classification, use a tool with an enum or structured outputs. To skip preamble, use a system-prompt instruction. To refresh context, inject reminders into the user turn. Ibid., "Migrating away from prefilled responses". Opus 5.5 and Fable 5.1 also reject forced tool use (tool_choice any/tool → 400): keep auto plus strict: true, or use structured outputs. What's new in Opus 5.5. Structured outputs (GA) use constrained decoding, so responses are always schema-valid. Unsupported: recursive schemas, numeric and string-length constraints, and additionalProperties other than false. The first use of a schema adds grammar-compile latency (cached 24 h from last use). Structured outputs.

Prompt-level hallucination guardrails. Allow "I don't know". On long documents, extract direct quotes first. Make Claude cite a supporting quote for each claim and retract claims it can't support. Restrict answers to the provided documents. Best-of-N comparison flags inconsistencies. Reduce hallucinations. Hard guarantees (schema, allowed labels) belong in structured outputs, not in prose.

Zero-shot, few-shot, chain-of-thought

Few-shot is "one of the most reliable ways to steer" format, tone and structure. Use 3–5 examples that are relevant and diverse, wrapped in <example>/<examples> tags. Prompting best practices. Prefer "diverse, canonical examples" over a "laundry list of edge cases". Context engineering.

CoT today = thinking + effort. General instructions ("think thoroughly") often beat hand-written step lists. Worked examples shape how Claude thinks. Manual CoT (reason, then put the answer in <answer> tags) is a fallback when thinking is off. On Fable 5.1, Opus 5.5 and Sonnet 5.5, rely on thinking instead: a prompt asking for written reasoning in <thinking> tags "may be declined". Explicit prompt chaining is still the right tool when you must inspect intermediate outputs. Ibid.

Context windows and token usage

Context is an attention budget. "As token count grows, accuracy and recall degrade": this is context rot. A 1M window is capacity, not a licence to fill it. Aim for "the smallest possible set of high-signal tokens". Load data just-in-time through identifiers (paths, queries), not up front. Context windows; Context engineering.

Token-count gotchas. The tokenizer introduced with Opus 4.7 (and used by later models) produces about 30% more tokens for the same text, so recount against the target model. Modular prompt design follows from the prefix rule. Stable content goes first (tool definitions, then system role, rules and examples). Per-session content (an uploaded document) goes next. Volatile content (the user's question, timestamps, user names) goes last. A timestamp at the top of the system prompt yields a 0% hit rate. To change instructions mid-session, append a {"role": "system"} message (a mid-conversation system message) instead of editing the top-level system field: the earlier prefix stays byte-identical, so the cache still hits. Prompt caching; Mid-conversation system messages.

Agent Skills = progressive disclosure for know-how. A Skill is a folder with a SKILL.md file (YAML name ≤ 64 chars, description ≤ 1024 chars that says what it does and when to use it), plus optional files and scripts. Level 1 metadata (~100 tokens per Skill) is always loaded. Level 2, the SKILL.md body (under 5k tokens), loads when triggered. Level 3 resources load only when read, and scripts run with only their output entering context. So you can install many Skills "without context penalty". On the API, Skills need the code-execution tool and run with no network access. Custom Skills don't sync across claude.ai, the API and Claude Code. Treat third-party Skills like installing software and audit them. Agent Skills overview; Equipping agents with Skills.

3 · Practice

A telecom routes 2 million short support messages a day into 12 queues. Each prompt is under 2k tokens and the p95 latency target is 500 ms. Which starting configuration is best?

  1. Claude Haiku 5.5 at low effort
  2. Claude Fable 5.1 at max effort
  3. Claude Opus 5.5 at xhigh effort
  4. Claude Sonnet 5.5 at max effort
High-volume, latency-sensitive classification is Haiku's stated sweet spot. Its lowest price applies to prompts ≤ 100k tokens, and low effort fits "simpler tasks that need the best speed and lowest costs". The others pay for reasoning depth that routing doesn't need. Validate with evals and step up only if accuracy falls short. Models overview; Effort.

An agent on Claude Opus 5.5 produces good results, but cost and latency are too high on routine subtasks. What should the architect try first?

  1. Lower the effort level and rerun the eval suite
  2. Set a budget_tokens cap on thinking for every request
  3. Send thinking type disabled to switch reasoning off entirely
  4. Move the workload to Claude Fable 5.1 for efficiency
The docs: tuning effort "is often a better lever than switching models". budget_tokens returns a 400 error on 4.7 and later models. Opus 5.5 rejects thinking: disabled (thinking is always on). Fable 5.1 costs more, not less. Choosing a model; Effort.

A legacy integration prefilled the assistant turn with { to force JSON. After migrating to Claude Sonnet 5.5, requests return a 400 error. Which two replacements are recommended?

  1. Use structured outputs with a JSON schema set in output_config
  2. Use strict tool use with a schema for required fields
  3. Keep the prefill but shorten it to one brace character
  4. Retry each rejected request with the prefill until it succeeds
Prefill on the last assistant turn is unsupported from the 4.6 models on, so any prefill fails and retries won't help. Structured outputs (JSON schema) and strict tool use guarantee schema-valid output through constrained decoding. Prompting best practices; Structured outputs.

A prompt combines a 60-page contract (≈ 45k tokens), review instructions and one question. How should it be ordered for best accuracy?

  1. Contract first in document tags, then instructions and the question
  2. The question first, then the contract, then the formatting instructions
  3. Instructions first, the question second, and the contract placed last
  4. The contract split into chunks interleaved with the repeated question
For 20k+ token inputs: put longform data at the top, wrap it in <document> tags, and put the query at the end. This improved quality "up to 30 percent" in tests. This order also caches well: the stable document stays in the prefix while questions change. Prompting best practices.

An invoice-extraction prompt yields inconsistent field formats and tone across vendors. Which change most reliably fixes this?

  1. Add three to five diverse, relevant examples inside example tags
  2. Add a single long example covering every possible field type
  3. Add thirty near-identical examples, all copied from the same customer
  4. Add capitalised MUST rules for format in the instructions section
Few-shot is "one of the most reliable ways to steer" format and tone. Use 3–5 relevant, diverse examples in <example> tags. Near-identical examples teach unintended patterns. One mega-example isn't diverse. Shouting rules is weaker than showing. Prompting best practices.

A team's prompt on Claude Opus 5.5 says "write your step-by-step reasoning in <thinking> tags before answering", and some requests get declined. What is the best fix?

  1. Remove it; rely on adaptive thinking and tune effort instead
  2. Rename the tags to scratchpad so the request is accepted
  3. Disable thinking so the manual reasoning steps can run instead
  4. Add a budget_tokens value so the written reasoning has room
On Fable 5.1, Opus 5.5 and Sonnet 5.5, prompts asking for written-out reasoning "may be declined". Rely on thinking, at lower effort if cost matters. Manual CoT is a fallback only when thinking is off, and Opus 5.5 can't turn it off. budget_tokens returns a 400 error on 4.7+. Prompting best practices; Thinking.

A chatbot sends a 6k-token system prompt and 20 tool definitions with every request, but the dashboard shows almost no cache reads. Which two are the likely causes?

  1. The current timestamp is inserted at the top of the system prompt
  2. The tool definitions are assembled in a random order on every request
  3. The system prompt is well above the model's minimum cacheable token length
  4. A breakpoint sits on the last block of the stable system prompt
Cache hits need a 100% identical prefix in the order tools → system → messages. Reordered tools invalidate everything. A changing timestamp early in the system prompt invalidates the system and messages levels. Being above the minimum length and placing a breakpoint at the end of stable content are both correct practice. Prompt caching.

Each night, 50,000 documents are summarised with the same 30k-token instruction block. Results are needed by 8 a.m. Which option minimises cost?

  1. Batch API with a one-hour cache on the shared prefix
  2. Batch API with a five-minute cache on the shared prefix
  3. Fast mode with a one-hour cache on the shared prefix
  4. Real-time Messages API with no caching of the shared prefix
Batch gives 50% off and the discounts stack with caching. Batches can run longer than 5 minutes, so the docs recommend the 1-hour cache for better hit rates. Fast mode is premium-priced and isn't available with batch. Batch processing; Pricing.

A research agent runs for hours. Its context fills with stale web-search results, and answer quality drops in later turns. Which two features address this most directly?

  1. Context editing that clears old tool results past a token threshold
  2. Server-side compaction that summarises the older turns of a long conversation
  3. Raising max_tokens so the agent has more room for each response
  4. Turning off prompt caching so stale content is not reused again
Quality falling as context grows is context rot. Tool-result clearing is the lightest fix for tool-heavy agents. Compaction is the primary strategy for long conversations. max_tokens limits output, not context hygiene. Caching changes price, not what's in context. Context windows; Context editing.

A coding agent migrates a monolith over many separate sessions across a week. Each new session wastes its first hour re-exploring the repo and re-deciding settled questions. What is the best fix?

  1. Add the memory tool so progress notes persist between sessions
  2. Use the one-hour cache TTL so sessions reuse earlier context
  3. Raise max_tokens so every session can read more repository files
  4. Switch to Fable 5.1 so the agent remembers earlier sessions
The memory tool lets Claude write and read files under /memories that your app stores, so a new session starts by reading the progress log instead of re-exploring. A cache only discounts an identical prefix and expires after an hour; it carries no state into a new session. max_tokens caps output, not memory. No model remembers past sessions on its own: state must live outside the context window. Memory tool; Context engineering.

An operations agent's system prompt contains 40 internal procedures of about 4k tokens each, but a typical task needs one or two. What is the best redesign?

  1. Package each as an Agent Skill loaded only when its description matches
  2. Keep them all in the system prompt and rely on prompt caching
  3. Spin up one subagent per procedure and send every request to each
  4. Move procedures into the user turn so they are counted as input
Skills use progressive disclosure: ~100 tokens of metadata per Skill until triggered, then the SKILL.md body. That's ~4k tokens of metadata instead of ~160k of procedures. Caching cuts the price but the tokens still fill the window, so context rot remains. Fan-out to 40 subagents multiplies cost. Agent Skills overview; Context windows.

You are migrating a high-volume workload from Claude Sonnet 4.6 to Claude Sonnet 5.5 and must update the cost forecast. Which two steps are correct?

  1. Recount prompts with the token counting endpoint using the new model ID
  2. Budget for thinking tokens, which bill as output and count toward max_tokens
  3. Reuse earlier token counts, because the tokenizer stays the same across generations
  4. Ignore cached prefix tokens, since they no longer count toward the window
Models from Opus 4.7 on use a newer tokenizer with ~30% more tokens for the same text: recount with the target model. Sonnet 5.5 has thinking on by default, and thinking is billed as output within max_tokens. Cached tokens still count toward the window. Token counting; Context windows.

An HR policy assistant sometimes states policies that aren't in the handbook it receives. Which two prompt-level guardrails most directly reduce this?

  1. Permit it to say it lacks enough information in the handbook
  2. Require a supporting handbook quote for each claim, else retract it
  3. Raise effort to max so the model reasons longer per question
  4. Assign a senior, world-class HR expert persona in the system prompt

4 · Architect scenario

Larkspur Legal sells a contract-review SaaS. Three workloads: (1) Intake: 50k uploaded documents a day must be classified into 9 contract types. (2) Review sessions: a lawyer uploads one contract (≈ 80k tokens) and asks about 8 questions over 20–40 minutes. Every request carries a 12k-token firm playbook and 15 tool definitions. (3) Re-review: when the playbook changes (monthly), all 200k active contracts are re-checked within 48 hours. Pain points: the API bill doubled last quarter, cache hits are rare, and lawyers report answers that cite clauses that don't exist.

(8 min) (a) Which model and effort for each workload, and why? (b) How do you structure the review prompt (order, tags, guardrails, output format)? (c) What is your caching and batch plan, and what was probably killing cache hits? (d) How do you manage context in long sessions, and is there a place for Skills?

(a) Intake: Haiku 5.5 at low effort, with output constrained to the 9 labels (structured outputs or a tool with an enum). Short prompts stay under Haiku's 100k-token price step. Review: start on Opus 5.5 (medium) or Sonnet 5.5 and let evals decide; run an effort sweep before switching tier. Don't use Haiku here: 80k contract + 12k playbook + tools + growing chat passes 100k, above which Haiku's prices jump 5× (cached tokens count toward that threshold). Re-review: the Batch API (50% off, 24 h window fits 48 h).
(b) Order: tools → system (role, playbook in <playbook>, 3–5 diverse worked examples in <examples>) → first user turn with the contract in <document> tags → question last. Guardrails: quote-first, cite a clause for each finding and retract unsupported claims, permission to say "not in the contract". Structured outputs for the findings table.
(c) Breakpoint 1 after the system prompt (tools + playbook shared by all sessions). Breakpoint 2 after the contract (shared by one session's questions). Automatic caching for the growing conversation. Use the 1-h TTL where gaps between questions exceed 5 minutes (pays off after two reads). For the batch, put the playbook prefix first with a 1-h cache. Likely killers: per-request content early in the prefix (user name, timestamp), tools reordered or toggled, editing the system prompt mid-session (append a mid-conversation system message instead), or changing top-level effort mid-session (use per-message effort). Turn on cache diagnostics to see exactly where the prefix diverged.
(d) 8 questions on an 80k contract fits in 1M, but context rot argues for keeping it lean. Use tool-result clearing for retrieval output and compaction for marathon sessions; the memory tool can keep per-matter notes across sessions. Skills: split the playbook into per-contract-type Skills (NDA, MSA, lease), loaded only when relevant. This shrinks every prompt but needs the code-execution tool, and changes what's in the cached prefix, so measure both.

  • Tiered models: Haiku for intake, stronger model for review, chosen by evals
  • Effort tuned before switching tier; Haiku >100k price step noticed
  • Batch API for re-review, with a 1-hour cache on the shared prefix
  • Stable → volatile ordering; documents top, question last; XML tags
  • Correct breakpoint placement and named causes of cache misses
  • Grounding guardrails (quotes/citations, "not found") + structured outputs
  • Context rot named; clearing/compaction; Skills as progressive disclosure
