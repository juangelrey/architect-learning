Stakeholder communication & lifecycle

The consultant's domain. Pin down success before you build, tell people honestly what a probabilistic system can do, and keep it working when models and prompts change.

≈ 20 minutes 3 review + 1 recall + 13 questions + 1 scenario D6

Where this material comes from. The blueprint lists five D6 task statements: discovery & requirements, communicating decisions & trade-offs, feedback loops / expectations / SLAs, documentation, and the lifecycle (discovery → design → handoff → monitoring → iteration). Exam guide §6, D6. The detailed official framing lives in the partner-only course. So this lesson leans on Anthropic docs and engineering posts where they exist. 0 · Spaced review

A client asks what the real difference is between the "workflow" and the "agent" you've proposed. Which statement is accurate?

  1. An agent steers its own process; workflows follow fixed paths
  2. An agent uses tools; a workflow never calls any tools
  3. An agent runs multiple models; workflows use only one model
  4. An agent has memory; a workflow cannot retrieve any documents
Control flow is the difference. Workflows orchestrate LLMs and tools through predefined code paths. Agents dynamically direct their own process and tool use. Both can use tools, retrieval and memory (the augmented LLM), and neither is defined by how many models it uses. Building effective agents.

A support bot's system prompt starts with a per-user greeting and timestamp, followed by a 6k-token static policy document. The cache hit rate is near zero. What is the fix?

  1. Put the static policy first and variable content after it
  2. Increase the cache TTL to one hour on every request
  3. Switch to a larger model with a bigger context window
  4. Add extra cache breakpoints inside the changing per-user greeting text
A cache hit needs a 100% identical prefix (tools → system → messages, up to the breakpoint). Because the variable greeting comes first, every request has a new prefix. A longer TTL doesn't help when the prefix never matches. A bigger model has nothing to do with caching. Breakpoints inside text that changes on every request still miss. Prompt caching.

An internal FAQ agent has read-only knowledge tools plus a delete_record tool it never needs. Security asks you to fix the configuration. Best action?

  1. Remove the unneeded delete tool from the agent entirely
  2. Keep the tool but log every invocation for auditors
  3. Keep the tool but require user confirmation each time
  4. Add a system prompt line forbidding use of deletion
Remove, don't monitor. Least privilege means the capability shouldn't exist. Logging only detects misuse after it happens. Confirmation prompts still leave the tool exposed. A prompt instruction is a soft control that injection can bypass. Exam guide, official sample items.

1 · Recall first

Without looking: (a) What four properties make a success criterion good, according to Anthropic's docs? (b) Define SLI, SLO and SLA in one line each. What single question tells an SLO from an SLA? (c) Name the five sections of a Nygard ADR. (d) List Anthropic's four model lifecycle states.

(a) Specific, Measurable, Achievable, Relevant. Example: "F1 ≥ 0.85 on a held-out set of 10,000 posts", not "classify sentiment well". Most use cases need several criteria at once. Define success criteria.
(b) SLI: a quantitative measure of some aspect of the service. SLO: a target value or range for an SLI. SLA: a contract with users that has consequences for meeting or missing its SLOs. Test: "What happens if the SLOs aren't met?" If there's no explicit consequence, it's an SLO. Google SRE book, ch. 4.
(c) Title, Context, Decision, Status, Consequences. Nygard.
(d) Active → Legacy → Deprecated → Retired. Requests to retired models fail. Model deprecations.

  • All four success-criteria properties
  • SLI/SLO/SLA correct, plus the "consequences" test
  • At least 4 of 5 ADR sections, including Consequences
  • Lifecycle states in order; retired = requests fail

2 · The ideas that matter

Discovery: define success before you design

Anthropic's own order of operations. Before prompt engineering you should already have (1) clear success criteria, (2) a way to test against them empirically, and (3) a first-draft prompt. "If not, spend time establishing that first." Prompt engineering overview. Good criteria are specific, measurable, achievable (grounded in benchmarks or prior experiments, "not unrealistic to current frontier model capabilities") and relevant. Usually they're multidimensional: task fidelity, consistency, relevance, tone, privacy, context use, latency, price. Define success criteria.

Feasibility and scope. Find "the simplest solution possible… This might mean not building agentic systems at all." Building effective agents. Not every failing criterion is fixed by prompting: "you can sometimes improve latency and cost more easily by selecting a different model". Prompt engineering overview. Start with one narrow, high-value use case, prove it against the criteria, then widen. Generic practice. It matches Anthropic's "start simple" advice.

Communicating decisions and trade-offs

ADRs (Architecture Decision Records). Each ADR is short (1–2 pages), numbered sequentially, and kept in the repo. Sections: Title, Context (the forces at play, stated neutrally), Decision ("We will…"), Status (proposed / accepted / deprecated / superseded), and Consequences (positive, negative and neutral). A reversed decision is not deleted: you mark it superseded and link the record that replaces it. Use ADRs for "architecturally significant" choices, meaning those that affect structure, non-functional characteristics, dependencies, interfaces or construction techniques. Nygard, "Documenting architecture decisions".

AudienceFrame the trade-off as…
ExecutivesBusiness metric vs cost per outcome. Error rate in plain numbers, plus the fallback (human review). Timeline and risk.
EngineersEval results per criterion, latency percentiles, token budgets, model and prompt versions, failure cases.
Security / legalData flows (a C4 context diagram), data retention and residency, tool permissions, HITL points, audit logs.

Generic practice (audience framing).

Cost × latency × quality. These pull against each other: "Agentic systems often trade latency and cost for better task performance." Building effective agents. The usual levers are model choice (the smaller models are faster and cheaper), routing, prompt caching and batching. Present a trade-off as an explicit choice with numbers. Never promise "all three".

Say non-determinism out loud. Agents behave differently from one run to the next ("a task that passed on one eval run might fail on the next"), so report success rates over repeated trials. pass@k is the chance that at least one of k tries succeeds. pass^k is the chance that all k succeed. At 75% per trial, pass^3 ≈ 42%. Use pass^k when consistency matters, as with customer-facing agents. Demystifying evals for AI agents. "Set temperature to 0" is not an answer: temperature, top_p and top_k are deprecated, and on Claude 4.7 and later models a non-default value returns a 400 error (the Python SDK v1.0+ drops them entirely). Model deprecations, API parameters.

Expectations, feedback loops, SLAs

SLI → SLO → SLA. Choose a few SLIs based on what users actually want. SRE advice on targets: don't base the target on current performance; keep it simple; avoid absolutes; have as few SLOs as possible; "perfection can wait" (start loose, then tighten). Keep a safety margin: an internal SLO tighter than the one you advertise "gives you room to respond". Don't overachieve, because users come to rely on what you actually deliver. Use percentiles, not averages, since averages hide the latency tail. An error budget (the allowed miss rate) tells you when it's safe to ship changes. Google SRE book, ch. 4. For LLM systems, the SLIs include quality ones (e.g. % graded correct on a weekly eval sample, escalation precision) alongside latency and availability. Generic practice applied to LLMs.

Your SLA can't be stronger than the platform beneath it. On the Claude API, the Standard tier is the default and runs with "best-effort availability". Rate limits (RPM, input and output tokens per minute, per model, set by usage tier) are "maximum allowed usage, not guaranteed minimums". Exceeding them returns 429 with a retry-after header. A sharp jump in usage can trigger acceleration limits, so ramp traffic up gradually. Hitting the tier's monthly spend cap also returns 429, but with no retry-after, and retries keep failing. 529 means the API is overloaded across all users. The SDKs retry transient errors twice by default with exponential backoff. Cache reads don't count toward input-token limits on most models, so prompt caching raises effective throughput. Priority Tier (99.5% uptime target) can no longer be bought; only existing commitments run until their end date. For guaranteed capacity, talk to sales. So: set internal SLOs and any contractual SLA with these limits in mind, and design retries, fallbacks and capacity headroom. Service tiers; Rate limits; API errors. API compatibility is stable: every request carries an anthropic-version header (currently 2023-06-01, which the SDKs set for you). Within a version, existing input and output parameters are preserved, but new optional fields and enum values can appear, so parse responses tolerantly. API versions.

"99% accurate" is not a requirement until you pin it down. Ask: accuracy of what, measured how, on which data, and what does a wrong answer cost? Then turn it into multidimensional criteria. Anthropic's example mixes F1 ≥ 0.85, 99.5% non-toxic outputs, "90% of errors would cause inconvenience rather than egregious error", and 95% of responses under 200 ms. Define success criteria.

Pilot → evaluate → scale. Demo ≠ production. "The last mile often becomes most of the journey". The gap between prototype and production "is often wider than anticipated". Start evals small: about 20 real-usage queries were enough to detect large effects (30% → 80%). Multi-agent research system. Or start with 20–50 tasks drawn from real failures. Demystifying evals. Evals should "mirror your real-world task distribution", including edge cases. A demo of hand-picked questions doesn't. Develop tests. Feedback comes in layers ("Swiss cheese"): automated evals, production monitoring, A/B tests, user feedback, manual transcript review and systematic human studies. "No single evaluation layer catches every issue." Ibid.

Lifecycle: model and prompt change is routine

Model IDs are pinned snapshots. From the 4.6 generation on, IDs are dateless (e.g. claude-sonnet-4-6, claude-sonnet-5-5), and the dateless ID is the snapshot, not an evergreen pointer. Anthropic never changes the weights behind an ID; an update ships under a new ID. (Older models have dated IDs such as claude-sonnet-4-5-20250929; their short aliases point to the latest dated snapshot.) Serving infrastructure (router, safety classifiers, sampling) can still cause minor behaviour drift. Model IDs and versioning.

Lifecycle states. Models move Active → Legacy (no more updates) → Deprecated (still works, replacement and retirement date assigned, "likely to be less reliable") → Retired (requests fail). Anthropic emails customers and gives at least 60 days' notice before retiring a publicly released model. Example as of October 2026: claude-sonnet-4-5-20250929 was deprecated on 30 Sep 2026 and retires on 30 Nov 2026, with claude-sonnet-5-5 as the replacement. To prepare, audit usage (Console → Usage → Export, a CSV broken down by API key and model) and test the replacement "well before the retirement date". These dates apply to the Claude API, Claude Platform on AWS and Microsoft Foundry. Amazon Bedrock and Google Cloud set their own schedules. Model deprecations.

Migrations have breaking changes. A model upgrade is more than an ID swap. Anthropic publishes a migration guide for each current model. Moving to Sonnet 5.5, for example, means sampling parameters, assistant prefill and forced tool_choice return 400 errors, and thinking budgets are replaced by effort levels ("run your evaluations at two or three levels"). In Claude Code, /claude-api migrate applies the code changes and produces a checklist of items to verify by hand. Migration guides; Sonnet 5.5 migration guide. Track the API release notes along with the deprecations page.

Re-run evals on every model or prompt change. Capability evals start with a low pass rate and give the team something to climb. Regression evals should stay near 100%. Teams that have evals can "upgrade in days". Teams without them may spend weeks testing. Demystifying evals.

Roll out gradually. Anthropic uses rainbow deployments, which gradually shift traffic from the old version to the new one "while keeping both running", because long-running agents can't all switch at once. Multi-agent research system. Roughly 70% of outages come from changes to a live system, hence progressive rollouts, fast detection and safe rollback. SRE book, intro.

3 · Practice

In a discovery workshop for an insurance claims-summarisation assistant, which two items must you establish before starting the architecture? (Choose two.)

  1. Whether claim files exist, are accessible, and are clean
  2. Latency, cost, and compliance limits the solution must respect
  3. Which vector database vendor the client's engineers prefer most
  4. How many subagents the final orchestration design will need
You can't design without knowing about data availability and quality or the constraints: they rule options in and out. Vendor preference is an implementation detail that comes later. Subagent count is an output of design, not a discovery input. Define success criteria (latency, price, privacy as criteria); framing is generic practice.

A client wants Claude to compute exact tax totals from structured ledgers. The rules are fully specified, and volume is millions of rows a day. What do you advise?

  1. Implement the rules in deterministic code; use Claude only for language
  2. Use the largest Claude model at maximum effort for every calculation
  3. Add few-shot examples until the model matches the rules engine exactly
  4. Run three Claude calls per ledger and take the majority answer
Part of feasibility is asking whether an LLM is the right tool at all. Fully specified rules belong in code, which is exact, cheap and auditable. Claude can still help where language matters (e.g. explaining a result). A bigger model, few-shot examples and voting all reduce error but never guarantee exactness, and they multiply cost at this volume. Building effective agents ("simplest solution possible").

A bank's CIO wants "Claude everywhere" across twelve departments this year. As the architect, what do you recommend first?

  1. Pilot one narrow, high-value use case with measurable success criteria
  2. Build a shared platform for all twelve departments before piloting
  3. Launch simultaneous pilots in every department to maximise early learning
  4. Pick the department with the loudest sponsor, ignoring data readiness
Start narrow, prove value, then scale. A platform built before any proven use case is speculative. Twelve parallel pilots spread eval and change-management effort too thin. Sponsor volume doesn't substitute for data readiness. Generic practice, consistent with Building effective agents.

Six months after launch, new engineers keep asking why the team chose RAG on a small model instead of a larger model with the whole corpus in context. What should have captured this?

  1. A short ADR recording context, decision, status, and consequences
  2. A code-level diagram showing every class in the service
  3. The slide deck from the original executive steering meeting
  4. A wiki page overwritten whenever the decision later changes
An ADR records the forces at play, the decision, and its positive and negative consequences, in the repo next to the code. A class diagram shows structure, not why. A slide deck loses the context and isn't maintained. An overwritten page destroys the history: superseded ADRs are kept and linked, never deleted. Nygard.

You're presenting a CFO with a decision to route most queries to a small model and hard ones to a larger model. Which two belong in the executive framing? (Choose two.)

  1. Cost per resolved query and the measured quality change versus today
  2. Expected error rate in plain numbers, plus the human fallback path
  3. Per-token input and output prices plus cache write multipliers per model
  4. The full prompt diff and routing classifier confusion matrix for review
Executives decide on business outcome vs cost and risk plus mitigation. Token price tables and confusion matrices are the right detail for the engineering review, not for the CFO. Generic practice (audience framing).

A sponsor asks, "Will the assistant give the same answer every time we ask the same question?" What is the honest, accurate answer?

  1. No; we measure consistency over repeated runs and design for variation
  2. Yes; setting temperature to zero makes current Claude models fully deterministic
  3. Yes; pinning the model ID guarantees identical outputs for identical inputs
  4. No; so we will skip evals because results cannot be measured
Outputs vary from run to run, so you report rates over repeated trials (pass^k when consistency matters). On Claude 4.7+ a non-default temperature returns a 400 error, and it never guaranteed determinism anyway. A pinned ID fixes the weights, not the sampled outputs. Variation is a reason to run more evals, not fewer. Demystifying evals; Model deprecations.

A client contract says the provider issues service credits if monthly p95 response latency exceeds 4 seconds. This clause is a…

  1. Service level agreement (SLA)
  2. Service level objective (SLO)
  3. Service level indicator (SLI)
  4. Error budget burn policy
It has a consequence (credits), so it's an SLA. p95 latency is the SLI, and "≤ 4 s" is the SLO it contains. An error budget is the allowed miss rate you use internally to pace releases. SRE book, ch. 4.

A pilot scored 97% correct on 200 eval cases. The sponsor wants to write "97% accuracy" into the client contract. Which two responses are sound? (Choose two.)

  1. Set the contractual SLA looser than the internal SLO target
  2. Start with a loose target, then tighten using production data
  3. Commit to the pilot's 97% because it was actually measured
  4. Promise 100% accuracy, since a human reviews every flagged answer
SRE: keep a safety margin (an internal SLO tighter than the advertised one) and perfection can wait (start loose, then tighten). Don't base targets on current performance, since 200 pilot cases aren't the production distribution. Avoid absolutes: human review of flagged answers does nothing about unflagged errors. SRE book, ch. 4.

A client wants a contractual 99.9% monthly availability SLA for an assistant that calls the Claude API on the default Standard tier. What is the sound response?

  1. Offer a looser SLA, with retries, fallbacks, and internal SLOs
  2. Sign 99.9% because Standard tier guarantees capacity for every request
  3. Buy a new Priority Tier commitment to inherit its uptime
  4. Raise max_tokens and rate limits so overload errors disappear entirely
Standard tier is best-effort, and rate limits are maximums, not guaranteed minimums. 429s and 529s (overload across all users) can still happen, so your SLA has to sit below what the platform supports, with retries, fallbacks and a tighter internal SLO. Standard guarantees nothing per request. New Priority Tier commitments are no longer sold, and its target was 99.5% anyway. max_tokens doesn't affect rate limits and does nothing about overload. Service tiers; Rate limits; API errors; SRE ch. 4.

A demo built on ten hand-picked questions impressed the board. In a limited beta, users hit many wrong or evasive answers. What is the right next step?

  1. Build an eval set mirroring real traffic, including edge cases
  2. Switch to the most capable model and rerun the demo
  3. Add the ten demo questions as few-shot examples to prompts
  4. Expand to all users quickly to collect more feedback faster
This is the demo-vs-production gap. Evals must "mirror your real-world task distribution" and include edge cases. Start with ~20–50 real cases and grow. A bigger model is a guess made without a diagnosis. Overfitting to the demo set hides the problem. Scaling a known-bad experience burns trust. Develop tests; Multi-agent research system ("last mile").

Anthropic emails that claude-sonnet-4-5-20250929, used in your production app, is deprecated and retires on 30 November 2026. Which two actions come first? (Choose two.)

  1. Run regression evals on the replacement model before cutting over
  2. Export the Console usage CSV to find every affected key
  3. Keep the deprecated model, since retired models still answer slowly
  4. Wait until retirement day, then swap the ID in production
Test the replacement well before retirement (regression evals), and audit usage through the Console Usage export, broken down by key and model, so no call site gets missed. Requests to retired models fail; they don't slow down. A swap on the last day leaves no time to fix breaking changes (on Sonnet 5.5, sampling parameters, prefill and forced tool choice return 400s) or to retune prompts and effort. Sonnet 5.5 migration guide. Model deprecations.

Your research agents run for up to an hour. A new prompt version broke agents that were mid-task when you deployed it. Which deployment approach prevents this?

  1. Rainbow deployment: keep both versions live and shift traffic over gradually
  2. Big-bang deployment: switch every running agent to the new version instantly
  3. Deployment freeze: wait until no agent anywhere is running any work
  4. Hotfix in place: patch the live prompt while running agents continue
Rainbow deployments keep both versions running while traffic shifts, so in-flight agents finish on the version they started with. Big-bang and in-place edits cause exactly this breakage. A freeze is impractical for a service that's always busy. Multi-agent research system.

The client's CIO and a security reviewer need one diagram showing the assistant, its user groups, and the external systems it touches (CRM, Claude API, identity provider). Which C4 view fits?

  1. A system context diagram
  2. A code-level class diagram
  3. A component internals diagram
  4. A deployment node diagram
The System Context diagram shows one system, its people and its external systems, for "both technical and non-technical people". Component and code views go inside the system, which is too much detail for this audience. Deployment is a supplementary infrastructure view. C4: system context.

4 · Architect scenario

Calloway Building Society (a made-up client). The COO saw a vendor demo and wants a customer-facing mortgage chatbot live in 4 weeks with "99% accuracy". The inputs are 300 PDF product sheets (some outdated), 18 months of contact-centre transcripts, and a core banking API that IT says is "hard to integrate". Compliance warns that anything resembling personalised financial advice needs regulated review. The current contact centre answers 70% of mortgage queries without escalation.

(8 min) (a) What do you ask in discovery, and how do you turn "99% accuracy" into criteria? (b) What do you scope for the 4 weeks, and what do you tell the COO? (c) Which SLI/SLO/SLA would you propose? (d) What do you document and hand off? (e) How do you keep it healthy after launch, including model changes?

(a) Discovery: the business outcome (containment rate? cost per contact?), users, data quality (which product sheets are current, and who owns them), integration (is account data needed at all in phase 1?), compliance boundaries, and latency and cost limits. "99% of what?" Split it into multidimensional criteria: answer correctness against current product sheets on a graded eval sample; correct refusal or escalation on advice-like questions (target near 100%); groundedness / citation present; p95 latency; cost per conversation. Benchmark against the human baseline (70% resolved without escalation), so the targets are achievable.
(b) Scope narrowly: read-only product Q&A over the curated, current sheets. No account data, no core banking integration, advice-like questions escalated to a human. Plan: week 1 discovery plus a 50–100-case eval set built from real transcripts, including edge cases; weeks 2–3 build and iterate against the evals; week 4 an internal or shadow pilot, not a public launch. Tell the COO honestly that outputs vary run to run, report rates from repeated trials, and show the error rate in plain numbers with the human fallback. Explain the demo-vs-production gap.
(c) SLIs: % correct on a weekly graded sample of production conversations, advice-escalation recall, p95 latency, availability. Internal SLOs tighter than anything in the contract. Leave the SLA (if any) for after the pilot produces production data: start loose, then tighten, and no "99%" absolutes. Keep it below what the Claude API tier supports (Standard is best-effort; plan for 429/529 retries and a fallback). Use an error budget to decide when prompt or model changes can ship.
(d) Docs: ADRs (e.g. "RAG over curated sheets; no account integration in phase 1"), a C4 context diagram for compliance and the CIO, an eval report (dataset, graders, per-criterion results), a prompt and model version record (pinned model ID), a runbook (bad answer reported, stale sheet, outage), and a handoff doc with owners.
(e) Lifecycle: monitor in layers (evals, production sampling, user feedback, transcript review), and feed bad answers into the regression set. Re-run regression evals on every prompt or model change. Track the deprecation page and release notes (≥ 60 days' notice), and test replacements early using the model's migration guide. Roll out gradually with rollback. Re-index when product sheets change.

  • Challenged "99%": defined what's measured and turned it into multidimensional criteria
  • Asked about data quality (outdated sheets) and compliance before design
  • Narrow phase-1 scope; advice questions escalated; 4 weeks = pilot, not full launch
  • Honest about non-determinism; error rates plus fallback for the exec
  • SLI → internal SLO → (later, looser) SLA within API tier limits; no absolutes; error budget
  • ADR + C4 context + eval report + runbook + handoff
  • Regression evals on model/prompt change; deprecation tracking; gradual rollout
