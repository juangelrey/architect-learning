D3 · I: Tools, auth & integration protocols

The biggest domain. Its favourite move: an agent with too much power, a token in the wrong place, or a context full of tools it doesn't need. Pick the fix that removes the problem.

≈ 18 minutes 3 review + 1 recall + 13 questions + 1 scenario D3

Versions taught. MCP 2026-07-28 (the current revision: stateless, no sessions), A2A v1.0, and the Claude API docs as of October 2026. Older terms appear only as one-line "formerly" notes. MCP changelog 2026-07-28; A2A spec.

0 · Spaced review

A market-intelligence team wants answers that need searching dozens of independent sources at once. The value per report is high and the information far exceeds one context window. Which design fits best?

  1. A lead agent delegating parallel searches to many subagents
  2. A fixed prompt chain searching the sources in sequence
  3. A router that sends each query to one source
  4. A single agent loading every source into its context
Breadth-first, parallelisable, high-value, more information than one window: this is exactly where orchestrator + subagents pays for its ~15× token cost. A chain can't adapt to the sources found. A router picks one handler. One agent with everything loaded hits context limits. Multi-agent research system.

An agent's backend rebuilds the tools array on every turn, adding or removing tools based on the user's last message. Prompt-cache reads are almost zero. What is the most likely cause?

  1. Changing tool definitions invalidates the whole cached prefix
  2. Tool definitions are never eligible for prompt caching
  3. The cache lifetime is shorter than one turn
  4. Cache breakpoints only apply to user message blocks
The cache prefix is built tools → system → messages, and changing tool definitions invalidates the entire cache. Keep the tool list stable. To load tools on demand without breaking the cache, use tool search with defer_loading: deferred tools are kept out of the prefix. The default TTL is 5 minutes and is refreshed on each hit. Prompt caching; Tool search tool.

A logistics firm needs real-time classification of 2 million short status messages a day, with a tight latency budget. According to Anthropic's model guidance, where should the team start?

  1. Fastest, cheapest model first; upgrade only for eval gaps
  2. Most capable model first; downgrade once the prompts stabilise
  3. A mid-tier model always, since it balances every trade-off
  4. Whichever model has the very largest available context window
Efficiency-first fits "tight latency requirements", "cost-sensitive" and "high-volume, straightforward tasks". Today that means starting with Haiku 5.5. Capability-first is for complex reasoning where accuracy outweighs cost. Either way, an eval set decides. Choosing a model.

1 · Recall first

Without looking: (a) What is token passthrough, and why does the MCP spec forbid it? (b) Name three tool-design moves that reduce capability bloat or context use. (c) What are the three MCP server primitives, and who controls each? (d) Name two ways to avoid loading every tool or instruction into context up front.

(a) An MCP server accepts a token that wasn't issued to it and forwards it to a downstream API. It's forbidden because it bypasses the server's controls (rate limits, validation), breaks audit trails, and lets a stolen token turn the server into an exfiltration proxy. The fix: the server MUST only accept tokens issued for itself, and gets a separate token for upstream calls.
(b) Give the agent only the tools it needs (least privilege). Merge multi-step chains into one tool (e.g. schedule_event). Use namespacing (asana_search). Write detailed descriptions. Return high-signal fields and readable names instead of UUIDs. Add pagination, filtering and truncation, plus a concise/detailed response format.
(c) Prompts: user-controlled (slash commands). Resources: application-controlled (context the client attaches). Tools: model-controlled (functions the LLM calls).
(d) Agent Skills (only name and description load at startup; the body loads when triggered). The tool search tool with defer_loading (Claude Code defers MCP tool definitions by default). Programmatic tool calling or code execution with MCP (intermediate results stay in the sandbox). Just-in-time retrieval through lightweight identifiers.

  • Passthrough = forwarding a token not issued to the server; audience validation is the fix
  • At least three tool-design moves (minimal set, consolidation, namespacing, descriptions, response shaping)
  • Prompts/resources/tools with user/application/model control
  • At least two progressive-discovery mechanisms

2 · The ideas that matter

Capability bloat: fewer, better tools

Remove, don't monitor. The official sample's lesson: least privilege means dropping tools the job doesn't need. Logging them or adding confirmation prompts is not enough. Blueprint heuristics. Anthropic names "bloated tool sets that cover too much functionality" as a common failure. The test: "If a human engineer can't definitively say which tool should be used in a given situation, an AI agent can't be expected to do better." Aim for a "minimal viable set". Context engineering. Narrow permissions also limit the blast radius: "An agent with read-only DB access … can be deployed far more broadly than one that writes to prod." How we contain Claude.

AuthN/AuthZ: where the security gaps hide

MCP authorization in one paragraph. Authorization is optional and applies to HTTP transports. A protected MCP server is an OAuth 2.1 resource server. It answers an unauthenticated request with 401 + WWW-Authenticate, pointing to its Protected Resource Metadata (RFC 9728), which names its authorization server. The client first requests the scope given in that challenge (least privilege). Clients MUST use PKCE, MUST send the resource parameter (RFC 8707) naming the target server, MUST check the iss in the authorization response against the issuer they recorded (RFC 9207, against mix-up attacks), and MUST put tokens in the Authorization: Bearer header, never the query string. Servers MUST validate that each token was issued for them (audience). stdio servers should not use this flow; they "retrieve credentials from the environment". MCP Authorization.

Client registration. A client gets its client_id in this order: (1) pre-registration if the client and server already know each other; (2) a Client ID Metadata Document (CIMD): the client_id is an HTTPS URL to a JSON document with client_name and redirect_uris, which the authorization server fetches and validates. This is the default when there's no prior relationship; (3) Dynamic Client Registration only as a fallback (deprecated in 2026-07-28); (4) ask the user. Client registration.

Prompt injection arrives through tool results. Prompt injections are "adversarial instructions hidden within the content that AI models process", and "no browser agent is immune". Mitigating prompt injections. "Tool output is an attack surface even when the tool is trusted." Defences that hold work at the architecture level: give granular tool permissions, use egress controls that block exfiltration "regardless of intent", and use sub-agents that isolate untrusted content and return "structured facts rather than raw text". MCP also says tool descriptions and annotations "should be considered untrusted" unless they come from a trusted server, and that hosts must get user consent before invoking tools. MCP spec overview. Skills follow the same rule: install only from trusted sources and audit them like software. Agent Skills.

Choosing the integration mechanism

MCP basics. MCP uses JSON-RPC between hosts (the LLM app), clients (connectors inside the host) and servers. Servers offer three primitives: prompts (user-controlled), resources (application-controlled) and tools (model-controlled). The one core client feature is elicitation (asking the user for input). MCP server features; Spec overview.

MCP is stateless. Every request carries its protocol version and client capabilities in _meta. A client can call server/discover to learn a server's versions and capabilities. There are no protocol sessions: a server that needs state across calls mints an explicit handle and gets it back as an ordinary tool argument. (Formerly an initialize handshake and an Mcp-Session-Id header; both removed in 2026-07-28.) Servers never send their own requests. When a tool call needs user input or an LLM completion, the server returns an input_required result and the client retries the call with the answers: Multi Round-Trip Requests (MRTR). This avoids "a shared storage layer across server instances" or "stateful load balancing". Sampling, Roots and Logging are deprecated: call your LLM provider directly, pass paths as tool parameters, and log to stderr or OpenTelemetry. Changelog; MRTR.

Transports. stdio: a subprocess the client launches on the same machine. Streamable HTTP: each message is a POST to one endpoint, and the reply is JSON or an SSE stream scoped to that request. Servers MUST validate Origin (to stop DNS rebinding) and should bind to localhost when run locally. Every POST carries MCP-Protocol-Version, Mcp-Method and, for tool, resource and prompt calls, Mcp-Name. These headers mirror the body so gateways can route and rate-limit without parsing it, and servers reject any mismatch. The 2024 HTTP+SSE transport is deprecated. Streamable HTTP. Long-running work uses the official Tasks extension (polling with durable handles). Spec overview.

Progressive discovery vs monolithic context

Context is "a finite resource with diminishing marginal returns". Find "the smallest set of high-signal tokens". Keep lightweight identifiers (paths, queries, links) and load data just in time. A hybrid works well: load a little up front (e.g. CLAUDE.md) and the rest on demand. Context engineering.

3 · Practice

A retailer's order-status agent has 38 tools from a shared MCP server, including issue_refund and delete_customer. Its job only needs order lookup and ticket creation. Security asks for least privilege. What should the architect do?

  1. Remove every tool that the order-status job never needs
  2. Log every refund and deletion call for later audit
  3. Require human confirmation before any refund or deletion runs
  4. Add a system prompt forbidding refunds and customer deletions
Remove, don't monitor. Least privilege means the capability isn't there at all. Logging only detects misuse after the fact. Confirmation prompts and prompt-level bans leave the capability in place, where an injection or a mistake can still reach it. Fewer tools also improve selection accuracy. Blueprint heuristics; Context engineering.

A scheduling agent calls list_users, then list_events, then create_event for every meeting request. It often fills its context with calendars and picks the wrong slot. Which tool redesign most directly helps?

  1. One schedule_event tool that finds availability and books it
  2. Separate list tools for each department to narrow results
  3. A larger context window so full calendars fit comfortably
  4. A stronger model so slot selection becomes more reliable
Anthropic's own example: consolidate a multi-step chain into one higher-level tool that matches the workflow. More list tools add bloat. A bigger window or a bigger model treats the symptom; the raw calendars still flood context. Writing tools for agents.

A CRM search tool returns 200 fields per record, including internal UUIDs and MIME types. The agent runs out of context and sometimes invents record IDs. Which two changes most directly fix this?

  1. Return readable names and only high-signal fields by default
  2. Add pagination, filtering, and a concise response format option
  3. Add a separate tool to retrieve each field group
  4. Ask the model to summarise each result before continuing
Shape the response: resolve UUIDs to natural-language identifiers (this cuts hallucinated IDs) and return only what the next step needs. Then add pagination, filtering and truncation with a response_format enum. More tools adds bloat. Asking the model to summarise happens after the tokens have already entered context. Writing tools for agents.

An internal MCP gateway receives the user's access token from the MCP client and forwards that same token to the HR system's API. HR's logs show calls with no gateway identity. What is the core flaw?

  1. Token passthrough; the gateway needs its own upstream token
  2. Missing PKCE; the client must add a code verifier
  3. Handle hijacking; the gateway must bind handles to users
  4. Transport choice; the gateway should switch to local stdio
Token passthrough is explicitly forbidden. It bypasses the gateway's controls, breaks accountability (HR can't tell who is calling), and lets a stolen token use the gateway as a proxy. The server must accept only tokens issued for itself and use a separate token, from the upstream authorization server, for HR. PKCE protects the code exchange, not this. State-handle hijacking is about guessed cart or workflow IDs, and no handle is involved here. Switching to stdio doesn't fit a shared remote gateway and leaves the token flaw unfixed. MCP security best practices.

A token issued for the company's CRM MCP server was replayed against its Finance MCP server and accepted. Which two controls from the MCP authorization spec close this gap?

  1. Servers validate that each token names them as audience
  2. Clients send a resource parameter naming the target server
  3. Clients place access tokens inside the URL query string
  4. Servers extend token lifetimes to reduce repeated reauthorization prompts
Bind tokens to a resource: clients MUST send the RFC 8707 resource parameter with the server's canonical URI, and servers MUST check the audience and reject anything else with 401. Tokens in the query string are explicitly forbidden. Longer lifetimes make theft worse; authorization servers SHOULD issue short-lived tokens. MCP Authorization; Security considerations.

An MCP proxy uses one static OAuth client ID with a third-party API, lets MCP clients register dynamically, and the third party remembers consent with a cookie. An attacker's link silently obtains a user's authorization code. What is the required mitigation?

  1. Per-client consent at the proxy before forwarding to third-party
  2. Longer-lived consent cookies issued by the third-party authorization server
  3. Wildcard redirect URI matching so all registered clients work
  4. Passing the third-party token straight through to MCP clients
This is the confused deputy attack. The proxy MUST keep a per-user registry of approved client_ids and show its own consent screen before redirecting to the third party. It must also match redirect URIs exactly (no wildcards) and use single-use state. Longer-lived consent cookies widen the hole. Passthrough is a separate anti-pattern. MCP security best practices.

A document MCP server lists files:*, db:* and admin:* in scopes_supported, and clients request all of them on first login. Most users only read files. What is the best redesign?

  1. Minimal scopes first; step up when an operation needs more
  2. One omnibus scope so users see a single consent screen
  3. Keep broad scopes but log every privileged tool call made
  4. Keep broad scopes but shorten refresh token lifetime to hours
Scope minimisation: scopes_supported should hold only the minimal set for basic use, and the server's 401 challenge can name the exact scope to request first. When a privileged operation is first tried, the server answers 403 insufficient_scope with the needed scope, and the client steps up (keeping the scopes it already has). Omnibus scopes and "publishing all possible scopes in scopes_supported" are listed as common mistakes. Logging and shorter lifetimes leave the blast radius as large as before. MCP Authorization; Security best practices.

An inbox-triage agent reads external customer emails, can query the CRM, and can send email. Red-teamers hid instructions in an email that made it forward CRM data outside. Which two controls most effectively reduce this risk?

  1. Egress controls that restrict outbound email to approved internal domains
  2. A sub-agent reads the emails and returns only structured facts
  3. A system prompt line telling Claude to ignore embedded instructions
  4. A larger model that is generally better at following instructions
Tool output is an attack surface. The defences that hold are architectural: egress controls that block exfiltration "regardless of intent", and isolating untrusted content in a sub-agent that returns structured facts, not raw text. A prompt line helps a little but is not a control, and no model is immune to injection. How we contain Claude; Prompt injection defenses.

A team built a stdio MCP server for its ticketing system and wants a backend service to use it through the Messages API's MCP connector (mcp_servers). What must change?

  1. Expose the server over HTTP at a publicly reachable URL
  2. Convert all the ticketing tools into MCP prompts and resources
  3. Embed the server's API key directly inside the system prompt
  4. Nothing; the MCP connector can launch local stdio servers directly
The MCP connector only reaches servers "publicly exposed through HTTP" (Streamable HTTP, or the deprecated SSE transport). Local stdio servers can't be connected directly, and only tools are supported, so converting to prompts or resources makes things worse. Auth goes in authorization_token, which you get through OAuth yourself. Never put it in the prompt. MCP connector.

A payments team runs its remote MCP server as 12 replicas behind a plain load balancer. One tool must get the user to confirm an amount before it charges. Under the current MCP spec, how should the server get that confirmation?

  1. Return input-required; the client retries the call with answers
  2. Pin each client to one replica with sticky sessions
  3. Mint an Mcp-Session-Id and share it across all replicas
  4. Push an elicitation request over a standalone GET stream
Multi Round-Trip Requests: the server returns an input_required result holding an elicitation/create request, plus optional requestState. The client asks the user and retries the original tools/call with the answers, and any replica can finish it. Treat requestState as attacker-controlled: integrity-protect it (HMAC or AEAD) if it affects authorization or business logic. Sticky sessions and Mcp-Session-Id belong to the session model removed in 2026-07-28. The standalone GET stream was removed too, and servers no longer send their own requests on any stream. MRTR; Streamable HTTP.

A procurement agent must hand long-running sourcing requests to a supplier's own AI agent. The supplier won't expose its tools, memory or prompts, and tasks take hours with progress updates. Which mechanism fits best?

  1. A2A, discovering the supplier agent through its Agent Card
  2. MCP, wrapping the supplier's internal tools as a server
  3. Direct API calls straight into the supplier's internal databases
  4. A shared prompt template both companies keep in sync
A2A is built for opaque agents that collaborate "without needing access to each other's internal state, memory, or tools". It supports long-running tasks (states, artifacts), streaming and push notifications, and discovery through an Agent Card. MCP would need the supplier to expose its tools, which it refuses; direct database calls break the same boundary; a shared prompt template is no protocol at all, with no task tracking. "A2A is about agents partnering on tasks; MCP is more about agents using capabilities." A2A spec; A2A and MCP.

An enterprise agent connects to nine MCP servers (about 220 tools, roughly 70k tokens of definitions). Tool selection errors are rising. Which two changes most directly address this?

  1. Enable the tool search tool and mark most tools deferred
  2. Keep the few most-used tools loaded and defer the rest
  3. Move every tool definition into the system prompt text instead
  4. Increase max_tokens so the model can reason about more tools
Selection accuracy degrades past 30–50 tools, and a typical multi-server setup burns ~55k tokens before any work starts. Tool search + defer_loading loads only the 3–5 tools needed per request. Keep the 3–5 most-used tools non-deferred. Moving definitions into the prompt is still monolithic context. max_tokens limits output, not input. Tool search tool.

A consultancy pastes 25 workflow playbooks (about 3k tokens each) into every agent's system prompt "in case they're needed". Most tasks use one playbook or none. Which change best applies progressive disclosure?

  1. Package each playbook as an Agent Skill with a clear description
  2. Compress all the playbooks into one much shorter combined system prompt
  3. Cache the playbooks so the long prompt costs less per call
  4. Split the playbooks across several agents that are chosen at random
Skills: only name and description (~100 tokens each) load at startup. SKILL.md (under 5k tokens) loads when the request matches the description, and extra files load only when needed. Caching cuts cost but still fills the context window and the attention budget. Compressing the playbooks loses detail. Random agent choice means the right playbook is often missing. Agent Skills.

4 · Architect scenario

Marlowe & Finch, an insurance broker with 2,000 staff, piloted an internal "ops copilot". The prototype is one agent with 140 tools from 9 MCP servers, all loaded up front: Salesforce, SharePoint, Jira, the claims database (including update_claim and approve_payout), email send, and others. Every server authenticates with one shared admin service account. A home-grown MCP gateway forwards each employee's Entra ID token to downstream APIs. The copilot also reads inbound broker emails. Next quarter they want it to request quotes from a partner underwriter, which runs its own AI agent and won't expose internal systems. Complaints: wrong tools picked, slow first responses, and an audit finding that "we can't tell who changed claim 88213".

(8 min) (a) Where is the capability bloat, and how do you fix it? (b) List the authN/authZ gaps and the fix for each. (c) Pick an integration mechanism for the internal systems and for the underwriter. (d) How do you move from monolithic to progressive context?

(a) Bloat: 140 tools for every task, with write and payout tools in an assistant that mostly reads. Split by job (e.g. a read-only research copilot vs a claims workflow). Remove approve_payout and update_claim from the general copilot. Put payouts behind a separate, human-approved workflow. Consolidate overlapping tools, namespace them (sf_, jira_, claims_), and shape responses (readable names, pagination).
(b) Shared admin account → user-delegated OAuth per employee with minimal scopes plus step-up; this restores per-user audit ("who changed 88213"). Gateway forwards Entra token → token passthrough. The gateway accepts only tokens issued for itself (audience check, resource parameter) and gets separate downstream tokens. If it proxies third parties with a static client ID, add per-client consent (confused deputy). Clients identify themselves with pre-registration (internal) or a Client ID Metadata Document, not Dynamic Client Registration (deprecated). Inbound emails → prompt-injection path to CRM data and email send. Isolate email reading in a sub-agent that returns structured facts, and add egress limits on email send. Secrets stay out of the agent's context and sandbox, with short-lived tokens.
(c) Internal systems: remote MCP over Streamable HTTP + OAuth (shared across hosts; stateless, so it scales behind a load balancer and gateways can route on the Mcp-Method/Mcp-Name headers), with a tool allowlist per agent. Prefer CLI tools where developers already use them. Partner underwriter: A2A, since it's an opaque agent with long-running quote tasks, discovered via its Agent Card and authenticated with a scheme declared on the card. Don't ask them to expose MCP tools.
(d) Turn on tool search with defer_loading, keeping 3–5 core tools loaded. Move procedures (claims handling, quote prep) into Agent Skills. For fan-out lookups and bulk data, use programmatic tool calling or code execution so intermediate data stays out of context. Measure tool-selection accuracy and time to first token before and after.

  • Removed write/payout tools from the general agent (not just logged them)
  • Identified token passthrough and the audience-bound fix
  • Replaced the shared admin account with per-user delegated, minimal scopes (fixes audit)
  • Treated inbound email as a prompt-injection vector, with an architectural control
  • A2A for the partner agent; MCP (HTTP + OAuth) for internal systems
  • Tool search / deferred loading and Skills to replace the monolithic context
