SLI · SLO · SLA

Google SRE book, ch. 4

  • SLI: a quantitative measure of the service. SLO: a target for an SLI. SLA: a contract with consequences. Test: "what happens if the SLOs aren't met?"
  • Don't base targets on current performance · keep it simple · avoid absolutes · as few SLOs as possible · perfection can wait (start loose, tighten).
  • Safety margin: internal SLO tighter than the advertised one. Don't overachieve. Percentiles, not averages.
  • Error budget = allowed miss rate → paces releases.
  • LLM SLIs include quality (% correct on a graded sample, escalation recall) as well as latency and availability. Generic
  • Platform ceiling: Standard tier = default, best-effort. Rate limits (RPM / ITPM / OTPM per model, by usage tier) are maximums, not guarantees. 429 + retry-after; ramp gradually (acceleration limits); spend-cap 429 has no retry-after; 529 = overloaded. SDKs retry twice with backoff. Cache reads don't count toward ITPM (most models). Priority Tier (99.5% target) no longer sold; existing commitments only. Your SLA must sit below this. Expectations & feedback

  • "99% accurate" → of what, measured how, on what data, and what does an error cost? Turn it into multidimensional criteria. Define success
  • Demo ≠ production: "the last mile often becomes most of the journey". ~20 real queries can detect large effects. Multi-agent research
  • Start with 20–50 tasks from real failures. Swiss-cheese layers: automated evals · production monitoring · A/B · user feedback · transcript review · systematic human studies. Demystifying evals
  • Evals mirror the real task distribution and include edge cases. Volume over hand-graded perfection. Develop tests

Lifecycle

Discovery → design → handoff → monitoring → iteration. Exam guide D6

  • Model states: Active → Legacy (no updates) → Deprecated (works, less reliable, replacement + retirement date) → Retired (requests fail). ≥ 60 days' notice by email. Audit: Console → Usage → Export (CSV by key and model). Test replacements well before retirement. Dates cover Claude API, Claude Platform on AWS, Microsoft Foundry; Bedrock and Google Cloud set their own. Oct 2026 example: claude-sonnet-4-5-20250929 deprecated 30 Sep, retires 30 Nov 2026 → claude-sonnet-5-5. Deprecations
  • IDs are pinned snapshots. 4.6+ dateless IDs are the snapshot (not aliases). Pre-4.6 dated IDs; their short aliases point to the latest dated snapshot. Updates ship as new IDs. Infrastructure changes can cause minor drift. Model IDs
  • Migrations break things: per-model migration guides (e.g. Sonnet 5.5: sampling params, prefill, forced tool_choice → 400; budgets → effort). Claude Code /claude-api migrate applies changes + verification checklist. Watch release notes. Migration guides · Release notes
  • Re-run evals on every change. Capability evals (low pass rate, room to climb) vs regression evals (≈100%). Teams with evals upgrade in days. Demystifying evals
  • Rainbow deployment: old and new run together while traffic shifts gradually, so long-running agents aren't broken mid-task. Multi-agent research
  • ~70% of outages come from changes → progressive rollout, fast detection, safe rollback. SRE intro
