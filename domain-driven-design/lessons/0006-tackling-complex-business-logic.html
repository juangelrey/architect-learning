Chapter 6

Tackling complex business logic

The domain model's building blocks: value objects, entities, aggregates, domain events, and domain services. The questions interviewers drill hardest.

0 · Spaced review: ch. 4–5

The business logic is simple and the data is flat. Which pattern does chapter 5 point to?

  1. Active record
  2. Domain model
  3. Event-sourced model
  4. Transaction script
Simple logic and simple data: a transaction script is enough. Reach for active record only when the data structures are complex. Ch. 5.

  1. Partnership pattern

1 · Recall first

Without looking: (a) What separates a value object from an entity? (b) Give at least three rules of aggregate design. (c) What is a domain service, and when do you need one?

(a) A value object is identified by its values: it has no ID, it's immutable, and two equal instances are interchangeable. An entity has an explicit identity that stays the same while its state changes. Entities live inside aggregates.
(b) An aggregate is a consistency boundary: only its own logic may change its state, through its public commands. It is a transactional boundary: commit one aggregate per transaction. It references other aggregates by ID only. It includes only the data that must be strongly consistent. It checks concurrency (for example, with a version field). Only the root is exposed. It publishes domain events.
(c) A domain service is a stateless object for business logic that doesn't belong to any single aggregate or value object, typically logic that reads several aggregates.

  • Value object vs entity: identity, immutability, equality
  • At least three correct aggregate rules
  • One aggregate per transaction and references by ID among them
  • Domain service: stateless, logic with no natural home

2 · The ideas that matter

Domain model (another Fowler pattern): an object model of the domain that holds both behavior and data, written in the ubiquitous language, with no infrastructure concerns. It's for complex logic: complicated state transitions, business rules, and invariants. Ch. 6.

  • Value object: identified by the combination of its values, and immutable. Use it to avoid "primitive obsession": an Email or Money type keeps validation and behavior in one place, and the code reads like the business. Use value objects wherever you can.
  • Entity: needs an explicit ID because its state changes over time. It isn't implemented on its own, only inside an aggregate.
  • Aggregate: an entity that enforces consistency for a cluster of objects. Its state changes only through its public interface (commands). It's committed in one transaction, and you change one aggregate per transaction. It references other aggregates by ID. It contains only what must be strongly consistent, and everything else is eventually consistent. It uses optimistic concurrency (a version field). The aggregate root is the only entry point.
  • Domain event: a past-tense message describing something significant that happened, part of the aggregate's public interface (TicketEscalated).
  • Domain service: a stateless home for logic that belongs to no single aggregate or value object, for example a calculation that reads several aggregates.

Why it works: these patterns encapsulate the invariants. Each object protects its own rules, so the number of states the system can reach shrinks, and with it the complexity.

See also Fowler, "DDD_Aggregate", "ValueObject", and Evans's DDD Reference.

3 · Practice

A customer's Address (street, city, postcode) has no meaning apart from its values, and two equal addresses are interchangeable. When the customer moves, the address is replaced, not edited. Model it as a…

  1. Entity class
  2. Domain service
  3. Value object
  4. Aggregate root
Identity comes from its values, it's immutable, and you replace it rather than edit it: a value object. The customer is the entity.

Why replace raw strings for emails and phone numbers with value objects?

  1. Validation and behavior live in one place, not scattered
  2. Strings cannot be persisted reliably in most relational databases
  3. Value objects carry IDs, making equality checks much faster
  4. Aggregates are strictly forbidden from containing any primitive fields
This cures primitive obsession: the rules travel with the type, and the code speaks the ubiquitous language. Value objects have no IDs.

Who may change an aggregate's state?

  1. Any application service that has loaded its inner entities
  2. Only the aggregate's own logic via its public commands
  3. Repositories directly updating its columns for better query performance
  4. Other aggregates holding a direct reference to its entities
An aggregate is a consistency boundary. If anything outside it could change its state, it couldn't guarantee its invariants. External code calls its commands, and the aggregate decides.

A use case wants to change two aggregate instances atomically. What does the chapter's guidance imply?

  1. Wrap both in one database transaction for safety
  2. Merge them into one aggregate regardless of consistency
  3. Use a domain service to update both atomically
  4. Modify one per transaction; reach the other eventually
One aggregate per transaction. Changes to other aggregates follow through eventual consistency, for example in reaction to domain events. If two pieces of data really must be strongly consistent, that's a reason to redraw the aggregate boundary, not to stretch the transaction.

When you're deciding whether some data belongs inside an aggregate, what's the guiding question?

  1. Must it be strongly consistent with the aggregate's other data?
  2. Is it stored in the same database table right now?
  3. Is it frequently displayed together on the same user screen?
  4. Does the same team own both pieces of this data?
Include only what the aggregate's invariants need to be strongly consistent. Keep aggregates as small as that allows. Anything else is referenced by ID and kept eventually consistent.

Two users change the same aggregate at the same time. How does the chapter suggest preventing lost updates?

  1. A global lock held for the whole session
  2. Last write wins, because conflicts are rare anyway
  3. A version field checked when committing (optimistic concurrency)
  4. Route each writer to its own database replica
The aggregate carries a version that's checked when committing. If someone else committed first, the second commit fails and can be retried using fresh state.

Calculating a shipping quote needs the cart contents, the customer's loyalty tier, and the carrier rates. These live in three different aggregates, and the calculation belongs to none of them. Put it in a…

  1. Value object
  2. Domain service
  3. Aggregate root
  4. Active record
A domain service is a stateless home for logic that spans aggregates or has no natural owner. It reads several aggregates. It isn't a way to change several of them in one transaction.

Which is a well-named domain event?

  1. EscalateTicket
  2. TicketService
  3. TicketUpdateDTO
  4. TicketEscalated
A domain event describes something that has already happened, so it's named in the past tense in the ubiquitous language. EscalateTicket is a command. The other two are technical artifacts.

4 · Interview scenario

Lendly runs peer-to-peer equipment rental, such as cameras and drills. Its core subdomain is how it manages risk. The rules:

  • An item can't be rented for two overlapping periods.
  • The deposit is calculated from the renter's trust score and the item's value.
  • An owner can file a damage claim up to 48 hours after the return. The claim can't exceed the deposit.
  • When an item is returned, the deposit is released or held, and both parties are notified.

(8 min) Design the domain model. Name the value objects, entities, aggregates and their boundaries (what goes inside, and what is referenced by ID), domain events, and any domain service. Say which invariant each aggregate protects.

ElementProposal
Value objectsMoney, DateRange, TrustScore, Deposit
Aggregate: ItemHolds its booked DateRanges. Invariant: no overlapping bookings. This must be strongly consistent per item, so it lives with the item.
Aggregate: RentalReferences ItemId and RenterId by ID. Contains the DamageClaim entity. Invariants: claim filed ≤ 48 h after return, and claim ≤ deposit. Both need the rental's own return time and deposit, so they belong inside it.
Domain serviceDepositCalculator: reads the renter's trust score and the item's value (two aggregates) and returns a Deposit.
Domain eventsRentalBooked, ItemReturned, DamageClaimFiled, DepositReleased. Notifications react to these, eventually consistent.

Booking touches both Item (reserve the period) and Rental (create it). That's two aggregates, so commit one per transaction and complete the other in reaction to an event. Alternatively, argue for a single aggregate if the business can't tolerate the brief gap. Interviewers want to hear you name this trade-off.

  • Used value objects for money, period, and score instead of primitives
  • Put the no-overlap invariant on a per-item aggregate
  • Kept the damage claim inside Rental, justified by its invariants
  • Referenced other aggregates by ID only
  • Used a domain service for the cross-aggregate deposit calculation
  • Domain events named in the past tense; notifications driven by events
  • Named the one-aggregate-per-transaction trade-off when booking
