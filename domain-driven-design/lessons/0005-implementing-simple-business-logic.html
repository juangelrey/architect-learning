Chapter 5

Implementing simple business logic

Not everything deserves a domain model. Two plain patterns cover most supporting subdomains, as long as you respect their pitfalls.

≈ 12 minutes 2 review + 7 questions + 1 scenario Part II

0 · Spaced review: ch. 1 & 4

  1. Anticorruption layer
  2. Shared kernel
  3. Conformist relationship

Supporting subdomains have simple logic, and that's exactly the territory of this chapter's patterns. Ch. 1.

1 · Recall first

Without looking: (a) Define transaction script and active record. (b) What must a transaction script guarantee? Name two ways that guarantee breaks in practice. (c) When would you choose active record over transaction script?

(a) Transaction script: business logic organized as procedures, each handling one request from the presentation layer. Active record: objects that wrap a data structure (such as a database row) and carry their own persistence methods. The logic is still script-like, but it operates on these objects.
(b) Each operation must be transactional: it succeeds completely or fails completely. It breaks when one operation has to update two systems (for example, write to the database and publish a message), which is an implicit distributed transaction. It also breaks when a retry repeats a non-idempotent operation.
(c) When the logic is still simple but the data structures are complex.

  • Both definitions correct
  • "Transactional: all or nothing"
  • Named a distributed-transaction pitfall
  • Named an idempotency or retry pitfall
  • Active record for complex data structures with simple logic

2 · The ideas that matter

Transaction script (a pattern from Fowler's Patterns of Enterprise Application Architecture): each public operation is a procedure that runs from start to finish. It's the simplest pattern, and its one hard requirement is to be transactional: the operation succeeds or fails as a whole. Ch. 5.

  • Pitfall: distributed transactions. If you update the database and then publish a message, a crash between the two leaves the system inconsistent. The same thing happens, less visibly, when you modify state and also return a result to a caller who never receives it. These are implicit distributed transactions. Chapter 9's outbox pattern addresses them.
  • Pitfall: retries. A non-idempotent operation (such as "increment the counter") that gets retried after a timeout runs twice. Make the operation idempotent, for example by having the caller pass the expected value or version (optimistic concurrency).
  • Fit: supporting subdomains and simple ETL-style work. Risk: as the logic grows, it gets duplicated across scripts.

Active record (also from Fowler): objects wrap the data structures and carry their own CRUD methods, which handles object–relational mapping for complex data. The logic is still organized as scripts. People sometimes call it the "anemic domain model" antipattern. The chapter's position is that it's a sound choice for simple logic and only becomes a problem when the logic is complex.

Be pragmatic. These patterns are tools, not moral failings. Pick them where the logic is simple, and move to a domain model when it isn't.

See also Fowler's catalog entries: Transaction Script, Active Record, and AnemicDomainModel.

3 · Practice

A transaction script organizes business logic as…

  1. Objects that wrap database rows and their persistence
  2. Aggregates enforcing invariants through a public command interface
  3. Procedures, each handling one request from the presentation
  4. Event streams replayed to derive the current state
One procedure per operation. The other options describe active record, a domain model, and an event-sourced domain model.

A script updates the database and then publishes a message to a bus. The process crashes between the two steps. What has been violated?

  1. The transactional behavior the script must guarantee
  2. The idempotency guarantee of the message consumer
  3. The aggregate boundary of the publishing entity
  4. The ubiquitous language of the bounded context
Two systems are updated, but not atomically. That's an implicit distributed transaction, which breaks the all-or-nothing guarantee. The book's fix comes in ch. 9 (outbox).

A script increments a page-visit counter. The client times out, retries, and the visit is counted twice. What's the right fix?

  1. Increase the client timeout so retries happen far less often
  2. Wrap the counter inside an aggregate that raises domain events
  3. Move the counter into the presentation layer's local memory cache
  4. Make the operation idempotent, for example via a version check
Retries are inevitable, so the operation has to be idempotent. One way is for the caller to send the value it expects (or a version), so that a repeated call is rejected or has no effect. A longer timeout only makes the bug rarer.

What distinguishes active record from transaction script?

  1. Business logic moves into rich aggregates with invariants
  2. Objects encapsulate data structures and their own persistence
  3. State is stored as an append-only event stream
  4. Procedures run without any database transaction at all
Active record adds objects that wrap data plus CRUD, which helps with complex data structures. The business logic is still organized as scripts.

A supporting subdomain edits a nested product catalog (categories → products → variants → attributes). The rules are basic validation. Which pattern fits?

  1. Transaction script
  2. Active record
  3. Domain model
  4. Event-sourced model
The logic is simple and the data structures are complex, so use active record. A domain model would be over-engineering here.

A reviewer calls your active record code "the anemic domain model antipattern". What is the chapter's view?

  1. Fine for simple logic; harmful only when logic is complex
  2. Always an antipattern; every context needs a rich domain model
  3. Never a problem, because active records cannot hold any logic
  4. Only acceptable in generic subdomains bought from large external vendors
Whether a pattern is right depends on the context. For simple logic, active record is appropriate. The "anemic" criticism applies when complex logic gets squeezed into this shape.

What's the main risk of using transaction scripts as the business logic grows complex?

  1. Too many aggregates locking the same database rows
  2. Event streams growing too large to replay quickly
  3. Duplicated business logic spread across many independent scripts
  4. Excessive layers of abstraction hiding simple procedural behavior
Scripts don't share a model, so the same rule ends up implemented in several places, and the copies drift apart. That's the point at which to switch to a domain model (ch. 6).

4 · Interview scenario

Courtly is a SaaS product for padel and tennis clubs. Its core subdomain is matching players by skill level. You own three supporting features:

  1. Price import: every night, read each club's CSV price list and load it into the database.
  2. Club profile: edit club → courts → surfaces → opening hours → holiday exceptions, with simple validation only.
  3. Cancel booking: mark the booking cancelled, ask the payment provider for a refund, and email the player.

(6 min) Choose a pattern for (1) and (2) and justify each. For (3), list what can go wrong with transactions and retries, and say how you'd mitigate it.

(1) Transaction script. Simple ETL with flat data. Make the import all-or-nothing per club, and make it safe to re-run (idempotent).

(2) Active record. The logic is simple but the data structure is deeply nested. Objects with CRUD methods handle the mapping.

(3) Risks: a crash between "mark cancelled" and "refund" leaves them inconsistent, because it's an implicit distributed transaction across the database, the payment provider, and email. A retry after a timeout can refund twice. Mitigations: commit the state change in a single local transaction and trigger the refund and email from it reliably (the outbox, ch. 9). Pass an idempotency key with the refund request. Make "cancel" a no-op when the booking is already cancelled.

  • (1) Transaction script, justified by simple logic and simple data
  • (2) Active record, justified by complex data structures
  • (3) Spotted the partial-failure or distributed-transaction risk
  • (3) Spotted the double-refund retry risk
  • (3) Proposed idempotency (key, version, or no-op on repeat)
  • (3) Proposed a reliable hand-off (single local transaction, then publish)
