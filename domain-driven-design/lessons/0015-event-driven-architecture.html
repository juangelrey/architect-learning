1 · Recall first

Without looking: (a) How does event-driven architecture differ from event sourcing? (b) Name the three types of event messages and what each one carries. (c) Why is it risky to publish an event-sourced aggregate's internal domain events to other services?

(a) EDA is about how components communicate: asynchronously, through events. Event sourcing is how one component persists its state. You can have either one without the other.
(b) Event notification: thin. It says something changed, and consumers query for the details. Event-carried state transfer: carries a snapshot of the state, so consumers can keep a local cache. Domain event: describes a business occurrence, and falls between the other two in content.
(c) Those events are an implementation detail of the producer's model. Consumers become coupled to its internals, and every refactor breaks them. Publish purpose-built public events and keep the internal ones private.

  • EDA = communication, event sourcing = persistence
  • Named all three event types
  • Explained what each one carries
  • Private vs public events: don't leak implementation details

2 · The ideas that matter

EDA ≠ event sourcing. EDA is an architectural style in which components communicate by exchanging events asynchronously. Event sourcing is a persistence pattern inside one component. They work well together, but neither one requires the other. Ch. 15.

Events vs commands. An event describes something that has already happened (past tense, so it can't be rejected). A command asks for something to happen, and it can fail.

Three types of event.

  • Event notification: a thin "X changed" message. The consumer queries the producer when it needs details, so it always reads the latest state but depends on the producer being available. It's also useful when the data is sensitive and shouldn't travel in a message.
  • Event-carried state transfer (ECST): carries the changed state, so consumers can keep a local cache and keep working when the producer is down. The cost is eventual consistency.
  • Domain event: a business occurrence modeled in the ubiquitous language. It sits between the other two in content.

Designing EDA well. Done carelessly, events produce a distributed big ball of mud, with services coupled through what their events contain and how they're timed. The chapter's guidance:

  • Assume the network will fail, so publish reliably with the outbox.
  • Separate private events (inside a context) from public events (its integration contract). Don't expose implementation details.
  • Choose the event type by the consumer's consistency needs: ECST when a local cache and eventual consistency are acceptable, event notification when the consumer must read the latest state.

See also Fowler, "What do you mean by 'Event-Driven'?", where the notification and state-transfer terms originate, and microservices.io, Transactional outbox.

Exchanging events between services is event-driven architecture. Event sourcing means a component stores its state as events. They're independent of each other.

  1. Event notification message
  2. Event-carried state transfer

With an event notification, the consumer fetches the current state when it reacts, so it doesn't rely on a possibly stale snapshot. The trade-off is a runtime dependency on the producer.

An event-sourced Campaign aggregate emits fine-grained internal events. Another team subscribes to all of them directly. What's the main risk?

  1. The broker will run out of storage quickly
  2. The events will arrive in the wrong order
  3. The consumer can no longer use any cache

Internal events mirror the producer's model internals. Expose a small set of public events as the integration contract, and keep the private ones private.

A service saves an order and then publishes OrderPlaced in a separate step. Occasionally the publish fails and downstream services never hear about the order. Which heuristic was ignored?

  1. Always prefer thin event notifications
  2. Use public and private events
  3. Assume the network will fail
  4. Align the services with subdomains
Publishing must be reliable. Use the outbox so the event is committed in the same transaction as the state change, then relayed at least once.

A patient-records service must announce changes, but the data is medically sensitive and shouldn't be copied around in messages. Which event type fits?

  1. Event notification message
  2. Event-carried state transfer
  3. Fully populated event
  4. Broadcast record snapshot
A thin event notification says only that something changed. Authorized consumers then fetch the details through a secured query, so sensitive data doesn't spread through the broker.

4 · Interview scenario

GreenCart, a grocery delivery service with three services. Catalog manages products and prices. Ordering takes orders and must show the correct price at checkout. Recommendations suggests products and needs product names, categories, and prices for millions of lookups a day. Today, Ordering and Recommendations call Catalog synchronously, and when Catalog is down, everything goes down. Catalog is event-sourced and has offered to "just publish all our internal events".

(7 min) Redesign the integration around events. For each consumer, choose an event type and justify it. Respond to Catalog's offer. Say how events are published reliably.

ConsumerEvent typeWhy
RecommendationsEvent-carried state transfer (ProductUpdated with name, category, price)High read volume and needs to survive Catalog outages. A slightly stale price in a recommendation is fine, so eventual consistency is acceptable.
OrderingEvent notification (PriceChanged) + query at checkout, or ECST with a price check at checkoutThe price shown at checkout must be correct, so it needs the latest state. Defend the trade-off: availability vs freshness.

Catalog's offer: decline it. The internal event-sourced events are private implementation details. Define a small set of public integration events (an open-host service with a published language).

Reliability: Catalog publishes through an outbox. Consumers handle duplicates idempotently, because delivery is at least once.

  • ECST for Recommendations, with eventual consistency acknowledged
  • Treated Ordering's need for fresh prices explicitly (notification + query, or a check at checkout)
  • Rejected publishing internal events and proposed public events
  • Outbox for reliable publishing
  • Mentioned idempotent consumers or at-least-once delivery
  • Distinguished EDA (integration) from Catalog's event sourcing (persistence)
