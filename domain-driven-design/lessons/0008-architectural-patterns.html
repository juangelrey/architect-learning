Chapter 8

Architectural patterns

Business-logic patterns decide how the rules are written. Architectural patterns decide how those rules connect to everything else.

≈ 12 minutes 2 review + 7 questions + 1 scenario Part II

0 · Spaced review: ch. 4 & 7

Which operation does an event store never allow?

  1. Appending events to a stream
  2. Reading a stream from start
  3. Modifying or deleting appended events
  4. Projecting events into read models
The event store is append-only, and history is immutable. Data deletion is handled with a forgettable payload, not by rewriting events. Ch. 7.

Your core context consumes a legacy upstream system with a messy, unstable model. Its team won't adapt to your needs. What protects your model?

  1. Conformist relationship
  2. Anticorruption layer
  3. Shared kernel
  4. Separate ways
An anticorruption layer translates the upstream model into yours. Conformist would import the mess into your core. Ch. 4.

1 · Recall first

Without looking: (a) Name the layers of layered architecture, what lives in each, and which optional layer can be added. (b) In ports & adapters, which way do dependencies point? (c) What does CQRS separate, and what are read models?

(a) Presentation: the program's public interface (UI, API, CLI, message subscriptions). Business logic: the rules. Data access: databases, message buses, external providers. Dependencies point downward only. The optional service layer sits between presentation and business logic, orchestrates operations, and manages transactions.
(b) Inward. Business logic is at the center and depends on nothing. It declares ports (interfaces), and the infrastructure provides adapters that implement them. That's dependency inversion.
(c) It separates the command execution model (strongly consistent, the source of truth) from any number of read models: precomputed projections, possibly in different databases, that can be rebuilt from the source of truth.

  • Three layers with correct contents
  • Service layer: orchestration + transactions
  • Ports & adapters: dependencies point inward, via interfaces
  • CQRS: one command model, many rebuildable read models

2 · The ideas that matter

Why architecture matters. Business logic shouldn't be scattered through UI handlers and SQL. Architectural patterns decide how the business logic relates to its inputs, outputs, and infrastructure. Ch. 8.

Layered architecture. Three layers: presentation, business logic, and data access. Each depends only on the layer below it. "Presentation" means any public interface, including APIs and message consumers. An optional service layer (also called the application layer) acts as a facade. It orchestrates use cases, manages transactions, and keeps presentation thin. The layered pattern fits transaction script and active record well.

Ports & adapters (also called hexagonal). It flips the dependency between business logic and infrastructure. The business logic sits at the center with no infrastructure dependencies, and infrastructure implements the business logic's interfaces. Onion and clean architecture follow the same principle. Because the domain model is kept free of technology, this pattern fits it well.

CQRS. Separate the model that executes commands from the models that serve queries. There's one strongly consistent command model, and as many read models as you need, each in whatever store suits it (polyglot persistence). Read models are read-only projections that can always be rebuilt. Projections can be synchronous (catching up from the source of truth with a checkpoint) or asynchronous (fed through a message bus, which brings ordering and duplication problems). CQRS is essential for an event-sourced domain model, because an event stream can't be queried flexibly.

Scope. These patterns aren't system-wide. Choose them per component, such as per bounded context, based on the business logic inside it.

See also Fowler, "CQRS".

3 · Practice

In layered architecture, a component that subscribes to a message bus and triggers business logic belongs to which layer?

  1. Domain layer
  2. Data-access layer
  3. Presentation layer
  4. Service layer
The presentation layer is the program's public interface: UI, API, CLI, and message subscriptions. The message bus used for outgoing events sits in data access.

What is the service layer's job?

  1. Holds the core business rules and invariants themselves
  2. Orchestrates business logic and manages transactions for clients
  3. Maps database rows to objects for all queries
  4. Renders the user interface and validates form input
It's a facade: it exposes use cases, orchestrates calls into the business logic, and wraps them in transactions. The business rules themselves live in the business-logic layer.

In ports & adapters, which way do dependencies point?

  1. Business logic depends on the infrastructure's concrete classes
  2. Presentation depends on data access, skipping business logic
  3. All layers depend on a shared utilities module
  4. Infrastructure depends on interfaces the business logic defines
Dependency inversion. The business logic owns the ports (interfaces), and infrastructure adapters implement them. That keeps the center free of technology concerns.

Why is ports & adapters a natural fit for a domain model?

  1. It allows the database to enforce all invariants
  2. It removes the need for an application layer
  3. It keeps business logic free of infrastructure concerns
  4. It forces every aggregate into a separate microservice
A domain model expresses complex rules in pure business terms, and persistence or framework code would pollute it. Ports & adapters isolates it. That's why the ch. 10 heuristic pairs the two.

In CQRS, read models are…

  1. The authoritative source of truth for all commands
  2. Precomputed projections that can be rebuilt from scratch
  3. Editable copies that commands write to directly first
  4. Always stored inside the command model's own database
Read models are read-only projections, and each can use whatever database suits its queries. Because the command model is the source of truth, any read model can be deleted and rebuilt.

A projection engine pulls new changes from the source of truth, tracking a checkpoint of the last change it processed. What kind of projection is this?

  1. A synchronous projection
  2. An asynchronous projection
  3. A dual-write strategy
  4. A saga process
Synchronous projections catch up from the source of truth using a checkpoint. Asynchronous ones receive changes over a message bus, which brings ordering and duplicate-delivery problems and makes rebuilding a projection harder.

A system has a core context built as a domain model and a supporting CRUD context. Which architecture should the whole system use?

  1. Ports and adapters everywhere, for consistency's sake
  2. Layered everywhere, since it's the simplest one
  3. CQRS everywhere, so every context can scale
  4. Choose per component; patterns needn't be system-wide
Architectural patterns are chosen per component, following the business logic each one contains. Forcing one pattern everywhere either over-engineers the simple parts or under-serves the complex ones.

4 · Interview scenario

ParkLoop runs a city parking app. Pricing is its edge: surge rules based on live occupancy-sensor feeds, events in the city, and loyalty status, implemented as a domain model. Permits is a set of resident-permit forms with basic validation. Citations is event-sourced because tickets are legal records, and enforcement wants to look up citations by license plate, see daily officer summaries, and view a heatmap of violations.

(7 min) Choose an architectural pattern for each of the three contexts and justify each choice. For Pricing, name two ports and their adapters. For Citations, design the read models and say how they're fed.

ContextArchitectureWhy
PermitsLayered (add a service layer if it uses active record)Simple logic. Anything more is overhead.
PricingPorts & adaptersA domain model needs to stay free of sensors, databases, and frameworks.
CitationsCQRSEvent-sourced, so queries need projections.

Pricing ports → adapters: OccupancyFeed → MQTT/HTTP sensor client · TariffRepository → Postgres · EventPublisher → message bus.

Citations read models: CitationsByPlate (key-value) · OfficerDailySummary (relational) · ViolationHeatmap (geo/search index). Feed them with synchronous, checkpointed projections from the event store. Each one can be rebuilt at any time.

  • A different pattern per context, justified by its business logic
  • Permits: layered (service layer only if needed)
  • Pricing: ports & adapters, with ports defined by the domain
  • Named concrete ports and adapters
  • Citations: CQRS with several purpose-built read models
  • Read models described as rebuildable projections
