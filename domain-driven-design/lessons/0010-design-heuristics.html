Chapter 10

Design heuristics

Parts I and II gave you the patterns. This chapter tells you which one to pick, and that decision is what interviewers ask you to defend.

0 · Spaced review: ch. 4–5

Business logic organized as objects that wrap database records and carry their own CRUD methods is called…

  1. Transaction script
  2. Active record
  3. Domain model
  4. Domain service
Active record objects wrap data structures and persist themselves. Use it when the logic is simple but the data structures are complex. Ch. 5.

A downstream team consumes an upstream model that is perfectly reasonable for its needs, and the upstream team won't adapt anything. The cheapest sensible pattern is…

  1. Anticorruption layer
  2. Shared kernel
  3. Conformist relationship
  4. Partnership agreement
If the upstream model is good enough, conformist avoids building a translation layer. Use an ACL when the upstream model is messy or when your context is core. Ch. 4.

2 · The ideas that matter

A heuristic is not a hard rule. It's a rule of thumb that's right in most cases, and it points you toward a good-enough decision quickly. Expect exceptions and know why you're making one. Ch. 10.

Bounded contexts. Wrong narrow boundaries are expensive to fix, because every change crosses contexts and teams. When a domain is volatile or poorly understood, which describes most new core subdomains, start with wider boundaries and split them once the model settles.

Business logic. The decision is driven by the complexity of the logic and the data, and by whether you need history:

  1. Does it involve money, need an audit trail, or need deep analysis of past behavior? → event-sourced domain model
  2. Otherwise, is the business logic complex? → domain model
  3. Otherwise, are the data structures complex? → active record
  4. Otherwise → transaction script

Subdomain type is a strong hint: core usually lands on 1 or 2, supporting on 3 or 4. The tree also works in reverse. If a supposed core subdomain fits a transaction script, check whether it is really core.

Architecture follows the logic pattern: event-sourced → CQRS (you need read models). Domain model → ports & adapters (keeps the model free of infrastructure). Active record → layered with a service layer. Transaction script → plain layered.

Testing follows too: domain models get a pyramid (mostly unit tests on aggregates and value objects). Active record gets a diamond (mostly integration tests). Transaction script gets a reversed pyramid (mostly end-to-end tests).

One-page summary: Heuristics cheat sheet. Background: Fowler, "CQRS".

3 · Practice

A core subdomain manages customer wallet balances. Regulators require a full history of every change, and finance wants to analyze how balances evolved. The business-logic pattern is…

  1. Transaction script
  2. Domain model
  3. Event-sourced model
  4. Active record
Money, an audit trail, and historical analysis are the triggers for an event-sourced domain model. The event stream is the history.

You've chosen a plain domain model (not event-sourced). Which architecture does the chapter pair with it?

  1. Ports and adapters
  2. Plain layered architecture
  3. CQRS with projections
  4. Layered with services
Ports & adapters puts the domain model at the center, free of infrastructure dependencies. CQRS is required for event sourcing. Layered variants suit the simpler patterns.

A context uses active record. Most of its tests should be…

  1. Aggregate unit tests
  2. End-to-end UI tests
  3. Manual exploratory sessions
  4. Integration tests mostly
Active record logic is entangled with persistence, so integration tests give the best value: the testing diamond. Unit-heavy pyramids are for domain models, and end-to-end-heavy reversed pyramids for transaction scripts.

A team insists its core subdomain is "just a few transaction scripts", and the logic really is that simple. What does the chapter suggest?

  1. Switch immediately to a full event-sourced domain model
  2. Revisit whether it truly is a core subdomain
  3. Add aggregates anyway so it looks more domain-driven
  4. Merge it into a neighboring generic bounded context
The heuristics run in both directions. Core subdomains are typically complex. If the logic is trivial, either the classification is wrong or the advantage won't last. Adding patterns for show is just accidental complexity.

Why does the chapter favor wider bounded contexts while a domain is still volatile?

  1. Fixing wrong narrow boundaries is much more expensive
  2. Wide contexts always perform better under heavy load
  3. Narrow contexts are forbidden for core subdomains entirely
  4. Wide contexts remove the need for ubiquitous language
Changes that cross boundaries need cross-team coordination and integration changes. Refactoring inside a wide context is cheap. Split once you understand the domain.

Which statement best describes the chapter's heuristics?

  1. Strict rules that must always be followed
  2. Defaults dictated by the chosen technology stack
  3. Rules of thumb holding in most cases
  4. Suggestions that apply only to greenfield projects
A heuristic gives a good-enough answer most of the time. In an interview, say when you'd deviate and why. That's what shows judgment.

An event-sourced domain model needs fast queries for dashboards. Which architecture follows from the heuristics?

  1. CQRS
  2. Layered
  3. Hexagonal
  4. Microkernel
Event streams can't be queried efficiently, so CQRS projects them into read models. That's why the tree pairs event sourcing with CQRS.

4 · Interview scenario

LoanLeaf is a peer-to-peer lending platform. Its edge is a credit-scoring engine with complex, constantly tuned rules. Repayments move money between borrowers and lenders, and regulators audit every cent. A loan-application form builder lets ops design multi-step forms with nested sections and conditional fields, but it has little real logic. A newsletter-preferences screen stores a few toggles per user.

(7 min) For each of the four areas, choose a business-logic pattern, an architecture, and a testing strategy. Justify each choice in one line, using the decision tree's questions.

AreaLogicArchitectureTesting
Credit scoringDomain model (complex logic). Event-sourced only if decision history must be audited.Ports & adaptersPyramid
RepaymentsEvent-sourced domain model (money + audit)CQRSPyramid
Form builderActive record (complex data, simple logic)Layered + service layerDiamond
Newsletter prefsTransaction scriptLayeredReversed pyramid

Strong interview move: argue that credit-scoring decisions may also need an audit trail ("why was this loan rejected?"), which would push it toward event sourcing too.

  • Repayments → event-sourced, citing money or audit
  • Credit scoring → domain model, citing complex logic
  • Form builder → active record, citing complex data and simple logic
  • Newsletter → transaction script
  • Correct architecture for all four
  • Correct testing strategy for all four
