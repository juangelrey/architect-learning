Chapter 7

Modeling the dimension of time

Don't store what the aggregate is. Store everything that happened to it, and derive the state.

≈ 12 minutes 2 review + 7 questions + 1 scenario Part II

0 · Spaced review: ch. 3 & 6

What determines which data belongs inside an aggregate's boundary?

  1. All entities sharing one database table
  2. Everything one team owns and maintains
  3. Data that must be strongly consistent
  4. Objects that appear on one screen
An aggregate is a consistency boundary. It contains only the data its business rules need to keep strongly consistent, and it's committed in one transaction. Keep it as small as that allows. Ch. 6.

How many teams can own a single bounded context?

  1. Two cooperating teams
  2. Exactly one team
  3. Every engineering team
  4. Domain experts only
Exactly one. A bounded context is an ownership boundary. One team may own several contexts, but a context is never shared between teams. Ch. 3.

1 · Recall first

Without looking: (a) In an event-sourced domain model, what is the source of truth, and how is current state obtained? (b) Name the benefits of event sourcing the chapter lists. (c) Name its drawbacks.

(a) The event store: an append-only stream of domain events per aggregate. Current state is a projection: load the events and replay them in order.
(b) Time traveling (rebuild the state at any past moment) · deep insight (the events can be projected into new models later) · audit log (a complete, reliable history) · advanced optimistic concurrency (conflicts detected with an expected version).
(c) Learning curve · evolving the model (events are immutable, so changing their schema is hard) · architectural complexity (more moving parts).

  • Event store / event stream as the source of truth
  • State derived by replaying events
  • At least three of the four benefits
  • At least two of the three drawbacks

2 · The ideas that matter

Event sourcing. A state-based model stores only an aggregate's current state, and the history of how it got there is lost. An event-sourced model stores every change as a domain event in an append-only event store. Current state is a projection, rebuilt by replaying the events. Other projections, such as reports or search models, can be built from the same events at any time. Ch. 7.

Event-sourced domain model. A domain model whose aggregates follow the same loop for every command: load the aggregate's events, rebuild its state, execute the business logic, and append the new events. The aggregate's state lives only in its events.

The event store is append-only. Events are never modified or deleted. Its interface is minimal: fetch an aggregate's stream, and append to it with an expected version. If the stream changed since you read it, the append fails. That's optimistic concurrency.

Trade-offs. You gain time travel, deep insight, a built-in audit log, and better concurrency control. You pay with a learning curve, harder model evolution, and architectural complexity. This is the costliest business-logic pattern. Chapter 10 reserves it for core subdomains, typically ones that handle money or need an audit trail or deep analysis.

FAQ from the chapter. Performance: long streams can be snapshotted, but most aggregates never need it. Deleting data: use a forgettable payload: encrypt personal data with a per-subject key and delete the key when needed. "Why not state plus a log file or table?" Two separate writes can drift apart. With event sourcing, the events are the state, so there's nothing to drift.

See also Fowler, "Event Sourcing".

3 · Practice

In an event-sourced domain model, an aggregate's current state is…

  1. Read from a snapshot table updated on every change
  2. Rebuilt by replaying its stored domain events in order
  3. Stored in a table, with events kept for auditing
  4. Cached in memory and periodically flushed to the database
The events are the source of truth, and state is derived from them. Keeping a table as the "real" state with events beside it for auditing is the state-plus-log approach that the chapter argues against.

Which operations does an event store need to provide?

  1. Fetch, update, and delete individual events by their ID
  2. Query by any field and overwrite outdated event payloads
  3. Insert events and periodically compact them into one row
  4. Fetch a stream and append with an expected version
The store is append-only: you fetch an aggregate's events and append new ones, with the expected version as a concurrency check. Updating or deleting events would destroy the history that's the whole point.

Two clerks modify the same aggregate at the same time. How does the event store detect the conflict?

  1. The last write silently overwrites the first
  2. A distributed lock is held for minutes
  3. Append fails if the stream version changed
  4. Both changes are merged automatically by timestamp
Optimistic concurrency. Each append carries the version the writer loaded. If someone else appended in between, the version no longer matches, so the append is rejected. The caller reloads, re-runs the command, and retries.

A customer exercises their right to be forgotten, but your events are immutable. What does the chapter suggest?

  1. Encrypt personal data per subject, then delete the key
  2. Rewrite every affected event, removing the personal data fields
  3. Delete the entire event stream and rebuild from snapshots
  4. Event sourcing cannot be used where personal data exists
This is the forgettable payload. Personal data is stored encrypted with a key per subject. Deleting the key makes that data unreadable, and the event stream stays intact.

Why not keep a normal state table and also write every change to a log file?

  1. Text files cannot be read by projection engines
  2. The two writes can't be committed atomically together
  3. Logging to files always violates the ubiquitous language
  4. Text files are too slow for production workloads
It's a dual write. If one write succeeds and the other fails, the log and the state disagree, and nobody knows which to trust. With event sourcing there's only one write: the events.

One aggregate's stream has grown to 50,000 events, and loading it is noticeably slow. What's the chapter's remedy?

  1. Delete old events
  2. Abandon event sourcing
  3. Merge event streams
  4. Take periodic snapshots
Snapshots: periodically persist the rebuilt state, then replay only the events after it. The chapter stresses that most aggregates never need this. A huge stream is often a sign the aggregate boundary should be reconsidered, so measure before you optimize.

Which subdomain best justifies an event-sourced domain model?

  1. Supporting subdomain editing simple reference data tables
  2. Generic subdomain bought from an external vendor
  3. Core subdomain handling money that needs auditing
  4. Any subdomain, since events are always better
It's the most expensive pattern, so it belongs where its benefits pay off: core logic involving money, legal audit trails, or deep analysis. The ch. 10 decision tree spells this out.

4 · Interview scenario

TipJar lets fans tip online creators. Each creator has a wallet. Tips come in, a platform fee is taken from each tip, creators request payouts to their bank, payouts can fail, and fans' banks sometimes reverse a tip (a chargeback). Finance must explain any balance to the cent, regulators ask "what was this creator's balance on March 3rd?", and creators can ask to have their personal data deleted.

(7 min) Design the Wallet as an event-sourced aggregate. (1) List its domain events. (2) Explain how the balance is derived. (3) Answer the regulator's question. (4) Handle a payout request that arrives at the same moment as a chargeback. (5) Handle data deletion.

(1) TipReceived · PlatformFeeCharged · ChargebackApplied · PayoutRequested · PayoutCompleted · PayoutFailed. Past tense, in business language.

(2) Replay the stream: add tips, subtract fees and chargebacks, hold amounts for requested payouts, release them when a payout fails. The balance is never stored as the source of truth.

(3) Time travel: replay only the events up to March 3rd. A projection can precompute daily balances for finance.

(4) Both commands load version n and try to append at n. One succeeds. The other's append fails on the expected version, so it reloads, re-runs, and retries. The payout is then checked against the balance after the chargeback.

(5) Keep personal data (name, bank details) out of events where possible. Where you can't, use a forgettable payload with a per-creator key that you delete on request.

  • Events named in the past tense, in business language
  • Balance derived by replay, not stored as the truth
  • Used time travel / projections for the historical question
  • Resolved the race with optimistic concurrency (expected version)
  • Handled deletion without mutating events (forgettable payload)
  • Justified event sourcing: core, money, audit
