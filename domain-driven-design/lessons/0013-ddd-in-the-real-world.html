Chapter 13

Domain-driven design in the real world

Most systems you'll meet are brownfield. DDD is still useful there, applied gradually and pragmatically.

≈ 12 minutes 2 review + 7 questions + 1 scenario Part III

Which ownership arrangement for bounded contexts is not allowed?

  1. One team owning several bounded contexts
  2. Two teams sharing one bounded context
  3. One team owning one bounded context
  4. Each context in its own repository
A bounded context is owned by exactly one team. One team can own several. Ch. 3.

An EventStorming sticky reads: "Whenever stock drops below the threshold, reorder." It's a…

  1. Command
  2. Aggregate
  3. Policy
  4. Event
"Whenever [event], then [command]" is a policy. Ch. 12.

1 · Recall first

Without looking: (a) How do you analyze a legacy system before you change anything? (b) What's the modernization order: logical vs physical boundaries, and which subdomains first? (c) What is the strangler fig pattern? (d) What is "undercover DDD"?

(a) Strategic analysis: understand the business domain and classify its subdomains, then map the current design. Which components implement which subdomains? Draw a context map of how they integrate. Then assess the tactical design of each component.
(b) Start with logical boundaries: reorganize the code into modules aligned with subdomains or bounded contexts. Move to physical boundaries later. Prioritize by business value, which usually means core subdomains whose current design hurts the most.
(c) Strangler fig: build new components next to the legacy system, route more and more functionality to them through a façade, and retire the old system once nothing is left.
(d) Applying DDD's principles and patterns without selling the label: just use the ubiquitous language, boundaries, and patterns where they help.

  • Business domain analysis before code changes
  • Mapping the current design / context map
  • Logical before physical; prioritize by value
  • Strangler fig described correctly
  • Undercover DDD described

2 · The ideas that matter

DDD isn't only for greenfield projects. Most real work is on existing systems. DDD's value there is in letting the business domain drive design decisions, not in adopting every pattern at once. Ch. 13.

Analyze first. Understand the business strategy and classify the subdomains. Then explore the current design: which components implement which subdomains, how they're integrated (draw a context map), and how each one is implemented tactically. Mismatches show you where to act. A core subdomain trapped in a big ball of mud is a strong candidate.

Modernize gradually. Start with logical boundaries by refactoring modules and namespaces to align with subdomains and contexts. Extracting physical services comes later. Prioritize by business value, not by technical irritation.

Strategic tools. Use the strangler fig pattern to replace legacy components incrementally behind a façade. During the migration, the old and new components may temporarily share a database, but only as a deliberate, short-lived exception. Use anticorruption layers to keep legacy models out of new code.

Tactical modernization. Refactor logic gradually toward the pattern the heuristics call for. For example, move from a transaction script to a domain model by first introducing value objects, then aggregates.

Pragmatism and "undercover DDD". You don't need management buy-in for the term DDD. Apply its ideas (ubiquitous language, bounded contexts, the patterns) where they pay off, and let the results make the case.

See also Fowler, "StranglerFigApplication".

3 · Practice

You join a team with a 10-year-old monolith. What's your first DDD step?

  1. Rewrite everything as microservices from scratch immediately
  2. Introduce aggregates into every existing module first
  3. Analyze the business domain and its subdomains
  4. Pick a new framework and migrate gradually
Start with strategic analysis: what the business does and which subdomains are core. Without that, you can't tell where modernization effort pays off.

Which modernization order does the chapter recommend?

  1. Logical boundaries first, then physical boundaries
  2. Physical boundaries first, then logical boundaries
  3. Both simultaneously, in one big release
  4. Only physical boundaries; logical are optional
Reorganizing modules inside the monolith is cheap and reversible, and it shows whether your boundaries are right before you pay for network calls and separate deployments.

New functionality is built beside the legacy system, a façade routes more and more requests to it, and the legacy system eventually disappears. This is the…

  1. Big-bang rewrite
  2. Shared kernel
  3. Bubble context
  4. Strangler fig
The strangler fig grows around its host until the host is gone. It's incremental, low-risk replacement.

During a strangler migration, the new and legacy components share one database. How does the chapter treat this?

  1. Strictly forbidden under any circumstances whatsoever
  2. A temporary exception during the migration
  3. The recommended permanent target architecture afterwards
  4. Only acceptable for generic subdomain components
Sharing a database is normally a coupling smell. During a strangler migration it's tolerated as a deliberate, temporary step, and removed once the legacy component is retired.

With limited budget, which legacy area should you modernize first?

  1. The core subdomain whose design hurts most
  2. The generic subdomain with the oldest code
  3. The supporting subdomain engineers find most annoying
  4. Whichever module has the lowest test coverage
Prioritize by business value. Core subdomains are where good design pays off. Generic ones are better replaced with bought solutions, and engineers' annoyance doesn't measure value.

Management is skeptical of "DDD". What does the chapter suggest?

  1. Abandon DDD until leadership formally approves it
  2. Present a DDD training plan to executives
  3. Apply DDD's practices without selling the label
  4. Adopt DDD only in brand-new greenfield projects
Undercover DDD: the value is in the practices (language, boundaries, patterns), not the name. Use them where they help.

A new bounded context must read customer data from the legacy monolith, whose model is a mess. To keep the new model clean, use…

  1. Conformist relationship
  2. Anticorruption layer
  3. Shared kernel
  4. Separate ways
An anticorruption layer translates the legacy model at the boundary, so the new context's model isn't shaped by the legacy one. It's a standard companion to the strangler fig.

4 · Interview scenario

"Here's our legacy system. Where would you start?" MediStock distributes medical supplies. It has a 12-year-old monolith with one huge database. Inside it: an order-routing module that picks the cheapest compliant warehouse (the company's edge, but tangled and full of bugs), invoicing (works fine), an in-house user-management module, and reporting (slow, but nobody complains). Leadership has never heard of DDD and wants "fewer incidents in routing".

(7 min) Give a step-by-step modernization plan: analysis, priorities, logical vs physical boundaries, which strategic and tactical tools you'd use, and how you'd pitch it to leadership.

  1. Analyze: classify subdomains. Routing is core, invoicing supporting, user management generic, reporting supporting. Map which modules implement what and how they couple (a context map).
  2. Prioritize routing: it's core and it hurts the most. Leave invoicing alone. Plan to replace user management with an identity product.
  3. Logical boundaries first: pull routing into its own module with an explicit interface inside the monolith.
  4. Tactical refactoring: move routing toward a domain model, introducing value objects first, then aggregates. Add unit tests as you go.
  5. Physical extraction later: strangler fig behind a façade, with an ACL against the legacy model. Accept a shared database only temporarily.
  6. Pitch: frame it as "fewer routing incidents, delivered incrementally", which is undercover DDD. No jargon is needed.
  • Started with business/subdomain analysis
  • Prioritized routing (core) by business value
  • Suggested buying a product for user management (generic)
  • Logical boundaries before physical extraction
  • Gradual tactical refactoring toward a domain model
  • Strangler fig + ACL, shared database only temporarily
  • Pitched it in business terms (undercover DDD)
