Communication patterns

How models talk across boundaries without corrupting each other, losing messages, or breaking consistency.

Which architecture keeps business logic free of any infrastructure dependency?

  1. Layered architecture
  2. Hexagonal architecture
  3. Microkernel architecture
  4. Monolithic architecture
Ports & adapters (hexagonal): the business logic defines the ports, and infrastructure implements them. In layered architecture, business logic depends on the data-access layer beneath it. Ch. 8.

A supporting subdomain with simple logic and simple data structures should be implemented with…

  1. Transaction script
  2. Active record
  3. Domain model
  4. Event-sourced model
Simple logic over simple data calls for a transaction script. Active record pays off only when the data structures are complex. Ch. 5.

1 · Recall first

Without looking: (a) What's the difference between stateless and stateful model translation? Give an example of each. (b) What problem does the outbox solve, and how? (c) What separates a saga from a process manager?

(a) Stateless translation converts each message or request on the fly. Examples: a proxy in an ACL or open-host service, or a message proxy that filters and transforms events. Stateful translation must remember data between messages. Examples: batching many small events into one message, or combining data from several sources.
(b) Committing an aggregate and publishing its events can't be one atomic step, so events may be lost or published for changes that never committed. The outbox stores the events in the same transaction as the aggregate, and a relay publishes them afterwards. Delivery is at least once.
(c) A saga matches events to commands: when this happens, do that, with compensating actions when a step fails. A process manager is a central, stateful coordinator for flows that need branching logic and an explicit start.

  • Stateless vs stateful, each with a valid example
  • Outbox: same transaction plus a relay
  • At-least-once delivery noted
  • Saga vs process manager: event→command matching vs central stateful logic

2 · The ideas that matter

Model translation. An anticorruption layer or open-host service needs a translation mechanism. Stateless translation happens on the fly. Synchronously, that's a proxy, which can be centralized in an API gateway. Asynchronously, it's a message proxy that subscribes to domain events, filters them, and transforms them, for example turning private events into public ones. Stateful translation needs its own storage. Two cases: aggregating incoming data (batching many messages into one), and unifying several sources into a single model. Ch. 9.

Integrating aggregates: the outbox. Domain events must be published only after the aggregate's state is committed. You can't make the database commit and the broker publish atomic. Publish too early and the event may describe a change that rolled back. Publish after the commit and a crash can lose it. The outbox commits the events in the same transaction as the aggregate. A relay then reads the unpublished events, by polling or by following the database's transaction log, and publishes them. Delivery is at least once, so consumers must be idempotent.

Saga. A long-running business process that spans several transactions. It listens to events and issues the matching commands, and it runs compensating actions when a step fails. Each aggregate stays strongly consistent, while the process as a whole is eventually consistent.

Process manager. When a flow needs central state and branching ("if the hotel is full, try the next one, else cancel"), a simple event→command saga isn't enough. A process manager is a central coordinator that tracks the process state, decides the next step, and is typically started explicitly.

See also microservices.io, "Transactional outbox" and "Saga".

3 · Practice

A downstream service calls an upstream API through a proxy. The proxy converts each response into the downstream model and keeps no data between calls. This is…

  1. Stateful model translation
  2. Transactional outbox relay
  3. Stateless model translation
  4. Saga process coordination
It translates on the fly, request by request, with no memory between calls, so it's stateless translation. It's typical inside an ACL (downstream) or an open-host service (upstream).

Which of these requires stateful model translation?

  1. Renaming fields of each request on the fly
  2. Forwarding requests unchanged to the upstream public API
  3. Filtering out private events before passing others on
  4. Batching many small events into one aggregated message
Batching means remembering the earlier messages until the batch is complete, so it needs state. Filtering and transforming events one at a time is stateless: that's a message proxy.

Why not simply publish the domain event right after the aggregate commits?

  1. Message brokers cannot accept events coming from aggregates
  2. The process may crash between commit and publish
  3. Events must be published before any commit happens
  4. Publishing after a commit violates the ubiquitous language
Commit and publish are two separate writes. A crash between them loses the event for good. The outbox turns them into one write (the database transaction) followed by a retryable publish.

What delivery guarantee does an outbox relay give, and what does that require of consumers?

  1. At-least-once delivery; consumers must handle duplicate messages
  2. Exactly-once delivery; consumers need no special handling
  3. At-most-once delivery; consumers must request lost messages
  4. Best-effort delivery; consumers must poll the database
The relay can crash after publishing but before marking an event as published, so that event gets sent again. Delivery is at least once, and consumers must be idempotent.

When a campaign is activated, it must be submitted to a publishing service. If the publisher rejects it, the campaign is marked as rejected. The component that reacts to these events and issues the commands is a…

  1. Projection
  2. Outbox
  3. Saga
  4. Aggregate
A saga matches events to commands across aggregates or contexts: CampaignActivated → submit for publishing, PublishingRejected → mark rejected. A projection builds read models and never issues commands.

When does the chapter suggest a process manager instead of a saga?

  1. When only one aggregate is involved in the process
  2. When the flow needs central state and branching logic
  3. When events must be stored in an outbox table
  4. When translating events between two separate contexts' public models
A saga is a straightforward mapping from events to commands. When the next step depends on accumulated state and if/else decisions, use a process manager: a central, explicitly started coordinator.

A saga coordinates an Order aggregate and a Payment aggregate. Which consistency guarantees hold?

  1. Both aggregates strongly consistent in one shared transaction
  2. Neither aggregate is consistent until the saga completes
  3. The saga enforces strong consistency with distributed locks
  4. Each aggregate strongly consistent; the process eventually consistent
Sagas don't break the aggregate rule that one transaction changes one aggregate. Each aggregate stays strongly consistent inside its own boundary, and the cross-aggregate process becomes eventually consistent, with compensations for failures.

4 · Interview scenario

TripNest books business trips. A traveler's request needs a flight, a hotel, and a rental car, each booked through a different supplier. If the preferred hotel is full, TripNest tries up to two alternatives. If none works, it cancels the flight. Every booking change must reach the Expenses context, a legacy system owned by another team that only accepts one consolidated daily report per traveler.

(7 min) (1) How do TripNest's aggregates publish their domain events reliably? (2) Saga or process manager for booking a trip? Sketch the steps, including the failure path. (3) How do you integrate with Expenses?

(1) Outbox: each aggregate's events are committed in the same transaction as its state, and a relay (polling or following the transaction log) publishes them. Delivery is at least once, so consumers dedupe by event ID.

(2) A process manager, started explicitly by BookTrip. It holds the trip's state: book the flight → book the hotel → if the hotel is full, try alternative 1, then alternative 2 → if all fail, compensate by cancelling the flight and notifying the traveler → otherwise book the car. The branching and accumulated state are why a plain saga isn't enough. Its commands also go out through the outbox.

(3) Stateful translation: a component subscribes to TripNest's public events, accumulates them per traveler, and once a day emits a consolidated report in Expenses's format. That's an ACL-style translator kept outside TripNest's core model, owned by whichever side the teams agree on.

  • Outbox, with the same-transaction write explained
  • Idempotent consumers / at-least-once delivery
  • Chose a process manager and justified it by branching and state
  • Included compensation (cancel the flight)
  • Expenses: stateful translation (aggregating into daily batches)
  • Published public events, not internal/private ones
